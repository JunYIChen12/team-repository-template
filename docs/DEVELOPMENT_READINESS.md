# 目标驱动的开发、运行与验收规范

版本：`v3.0.0`

## 1. 目的与适用范围

本规范规定团队如何把一个 Issue、变更或验收任务推进到可验证的结果。它适用于代码、配置、数据迁移、容器、外部服务和 IoT 项目。

核心原则是：先证明最短路径可以到达用户目标；安全、资源和证据要求附着在这条路径上，不单独形成一条串行流程。

本规范不替代项目领域规则、信息安全制度或发布审批。项目可以增加更严格的约束，但不能降低本规范的隔离、授权和真实验收要求。

## 2. 术语和状态

### 2.1 术语

- **目标**：用户可以观察或操作的最终结果。
- **主线**：达到目标所需的唯一运行、发布或处理路径。
- **侧线**：有价值但不阻塞当前目标的工作。
- **门禁**：在一次状态改变前必须确认的安全或运行条件。
- **证据等级**：静态检查、运行检查、用户入口验收三者分别记录，不能互相替代。

### 2.2 状态

| 状态 | 含义 |
| --- | --- |
| `NOT_READY` | 目标、主线或必要授权尚未明确。 |
| `READY` | 已选定主线，隔离和回滚边界可复核。 |
| `IMPLEMENTING` | 正在修改代码、配置或任务级资源。 |
| `RUNNING` | 最小运行组合已真实启动并通过对应健康检查。 |
| `ACCEPTING` | 正在从用户指定入口执行验收。 |
| `ACCEPTED` | 指定验收人确认目标结果。 |
| `CLOSED` | 临时资源、证据、回滚和遗留项已收束。 |
| `BLOCKED` | 缺少前置条件；必须写明缺什么、责任人和最小下一步。 |

构建成功、容器健康、接口返回 `200` 或文件已登记，都不能单独证明 `ACCEPTED`。

### 2.3 参考依据

本规范吸收 [ISO/IEC/IEEE 12207](https://www.iso.org/standard/90219.html) 的生命周期思想、[ISO/IEC/IEEE 29119](https://committee.iso.org/sites/jtc1sc7/home/projects/flagship-standards/isoiecieee-29119-series.html) 的测试过程、[IEEE 1012](https://standards.ieee.org/ieee/1012/12536/) 的验证与确认原则，以及 [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final) 的安全开发实践。它们提供原则；本文件定义团队的最小执行规则。

## 3. 执行模型

每个目标只走以下六步。纯代码任务可跳过不适用的运行步骤；外部设备任务可增加领域扩展，但不得把不适用的步骤变成阻塞。

### 3.1 定义目标

在 Issue 或任务记录中写清：

- 用户目标和可观察的完成信号；
- 范围与非目标；
- 验收入口、验收人和通过条件；
- 当前代码或配置基线；
- 需要单独批准的资源或动作。

没有完成信号的任务保持 `NOT_READY`，不进入实施。

### 3.2 选择唯一主线

在任何写入前，完整阅读实际入口：启动脚本、发布脚本、Compose、迁移命令、包脚本和调用链。

主线必须明确：

- 哪些进程、服务、数据和身份真的需要；
- 启动顺序、就绪信号和停止方式；
- 哪些服务明确不启动；
- 现有命令是否足够，或需要一个最小任务级包装。

同一目标不得同时维护两套运行方案。发现现有入口会启动无关服务时，优先复用已有的更小命令组合；只有没有组合时才新增最小包装。

### 3.3 一次性预检

在主线第一次状态改变前，记录：

- Git SHA、工作树状态和变更范围；
- 目标路径、磁盘空间、端口、进程、容器、网络、卷和数据归属；
- Secret 引用、最小权限、有效期和撤销方式；
- 回滚范围和不可触碰的稳定或生产资源。

安全预检在资源、权限或主线变化前复做；不能因为一个小动作重复生成完整预检。未知资源一律保留并报告。

### 3.4 运行最小组合

只启动实现目标所需的最少进程和依赖。数据库迁移、bootstrap、业务配置写入、Secret 导入、服务重启、流量切换和回滚属于串行动作，必须有明确责任人和回读。

项目级配置必须优先通过正式 UI 完成。只有 UI 无法完成且负责人批准时，才允许受控后台操作，并将 UI 缺口记录为 Issue。

### 3.5 从用户入口验收

验收必须使用用户指定的真实入口，例如 UI、正式查询、设备场景或发布产物。静态检查、日志、API 和数据库可以辅助诊断或准备隔离数据，但不能替代要求中的真实验收。

每个验收场景记录输入、操作、实际结果、基线、证据等级和未覆盖范围。连续两次失败且没有新的代码、数据、环境或契约证据时，停止重跑并先归因。

### 3.6 恢复与收束

停止任务级资源，验证重启或恢复要求，回读 Git、进程、端口、容器、磁盘和临时资源。结案记录只保留：目标结果、实际基线、关键命令、证据位置、回滚方式、遗留项和责任人。

数据迁移、稳定环境切换和生产流量变更必须作为独立目标，不能从候选验收自动推导。

## 4. 门禁和并行规则

### 4.1 三类门禁

| 门禁 | 解决的问题 | 何时执行 |
| --- | --- | --- |
| 安全门禁 | 会不会泄露密钥、修改稳定数据或触碰生产资源？ | 第一次状态改变前，或边界改变时。 |
| 运行门禁 | 最小服务组合是否隔离、可启动、可回滚？ | 启动前。 |
| 验收门禁 | 用户入口是否完成目标场景？ | 宣称完成前。 |

八层架构、分层设计或项目领域模型用于归因和责任分配，不自动构成串行门禁。每个目标必须把每层标为 `适用`、`后置` 或 `不适用`。

### 4.2 主线和侧线

可以并行：静态审查、测试设计、Issue 分类、文档核对和不共享资源的代码工作。

必须串行：迁移、恢复、Secret 导入或轮换、业务配置写入、服务重启、流量切换和回滚。

性能、长期运行、硬件采集、运维治理和数据迁移等侧线不得阻塞不依赖它们的 UI 或功能验收。

## 5. 协作和阻塞处理

每个协作任务只包含：明确输入、一个动作、一个可验证输出、停止条件和时间盒。超时必须返回 `可继续`、`失败` 或 `需要决策`，不能无限排查。

`BLOCKED` 记录必须包含：

1. 缺失条件及其证据；
2. 对目标的影响；
3. 责任人；
4. 至少一种最小解决方式；
5. 选定后的下一步。

禁止用重复执行相同命令代替归因。出现新证据后才允许重试。

## 6. 最小追踪和证据

每个目标只保留以下长期材料：

1. 目标记录：Issue、目标、非目标、验收条件；
2. 运行清单：版本、资源、Secret 引用、回滚；
3. 启动入口：现有命令或最小任务级包装；
4. 验收记录：用户操作和实际结果；
5. 结案回执：状态、遗留项和资源收束。

证据不得包含密码、Token、证书、明文连接串、客户数据或不必要的敏感日志。临时文件和可重建资源不得提交到 Git。

## 7. 例外

不能满足本规范时，负责人必须记录未满足项、原因、影响、替代控制、批准人和失效时间。例外不能成为绕过稳定环境、安全边界或真实验收的长期方式。
