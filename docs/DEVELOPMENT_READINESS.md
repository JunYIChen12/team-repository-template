# 软件开发前置门禁、测试与验收规范

版本：`v1.2.0`

## 1. 目的与适用范围

本规范用于防止开发任务在实现阶段结束后才暴露接口、数据、环境或验收条件缺失的问题。它适用于采用本仓库协作规范的软件项目，尤其适用于包含数据库、消息系统、容器、外部设备或多服务依赖的项目。

本规范不替代项目的领域规则、信息安全制度或发布审批制度。项目可以增加更严格的要求，但不得降低本规范的强制门禁。

## 2. 规范性依据

本规范参考以下公开标准和技术规范：

- [ISO/IEC/IEEE 12207](https://www.iso.org/standard/90219.html)：软件生命周期过程。
- [ISO/IEC/IEEE 29119](https://committee.iso.org/sites/jtc1sc7/home/projects/flagship-standards/isoiecieee-29119-series.html)：软件测试过程和测试文档。
- [ISO/IEC/IEEE 29119-2:2021](https://www.iso.org/standard/79428.html)：测试过程，覆盖测试计划、分析、设计、执行和完成。
- [ISO/IEC/IEEE 29119-3](https://committee.iso.org/standard/56737.html?browse=ics)：测试文档和测试记录示例。
- [IEEE 1012-2024](https://standards.ieee.org/ieee/1012/12536/)：验证与确认过程，检查产品是否满足要求和用户预期。
- [ISO/IEC 25010](https://www.iso.org/standard/78176.html)：软件产品质量模型。
- [NIST SP 800-218 SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)：安全软件开发实践。
- [OpenAPI Specification](https://spec.openapis.org/oas/)：HTTP API 契约。
- [OASIS MQTT Version 5.0](https://www.oasis-open.org/standard/mqtt-v5-0-os/)：消息通信契约。
- [Compose Specification](https://github.com/compose-spec/compose-spec)：容器服务、网络、卷和健康检查定义。
- [SLSA Specification](https://slsa.dev/spec/v1.0-rc2/)：软件供应链和构建来源证明。

公开标准提供原则和技术依据；本文件定义项目必须执行的具体门禁。

## 3. 术语和状态

“必须”表示强制要求；“应”表示默认要求，例外必须记录原因。

每个任务分别记录以下状态，不得互相替代：

- `NOT_READY`：开发前置条件未满足。
- `IN_PROGRESS`：已满足前置条件，正在开发。
- `CODE_COMPLETE`：代码已完成并提交，但尚未完成全部验证。
- `DEVELOPMENT_COMPLETE`：聚焦测试、质量检查和审查证据齐备。
- `DELIVERABLE`：隔离环境验证、回滚和运行证据齐备。
- `ACCEPTED`：需求方或指定验收人完成正式验收。
- `BLOCKED`：存在已记录且尚未解除的阻塞。

提交、构建成功或单个测试通过，都不能单独证明任务已验收。

## 4. 开发前置门禁（Definition of Ready）

任务进入开发前，负责人必须确认以下内容已经写入 Issue 或关联设计记录：

### 4.1 需求和范围

- 背景、目标、范围和非目标明确。
- 负责人、协作角色、依赖任务和风险明确。
- 正常流程、异常流程和边界条件明确。
- 验收人、验收环境和验收命令明确。

### 4.2 契约

- API 的请求字段、响应结构、状态码、错误格式和认证要求与 OpenAPI 或项目契约一致。
- 数据库表、迁移、兼容性和回滚要求明确。
- MQTT Topic、消息版本、QoS、retain、时间戳、幂等键和权限范围明确。
- 外部设备或第三方服务的可用性、超时、重试和降级行为明确。
- 代码、测试、文档和配置不得使用不同版本的同一契约。

### 4.3 测试数据

- 存在可重复获取或生成的任务级测试数据。
- 每个边界输入都有预期结果和质量语义。
- 计数器回退、重置、重复事件时间、缺失数据和异常消息等特殊数据必须明确是否需要受信事件或额外前置条件。
- 测试数据不得来自共享生产库，不得包含未经授权的客户数据或凭据。

### 4.4 工具和环境

- 运行时、包管理器、依赖版本、容器引擎和测试工具已确认可用。
- 服务启动顺序、健康检查和就绪条件已定义。
- 数据库、Broker、网络、卷、端口、日志和凭据的任务归属明确。
- 任务可以在隔离环境中启动、重置和清理。
- 环境问题和业务代码问题有明确的区分方式。

不满足以上条件时，任务应保持 `NOT_READY` 或 `BLOCKED`，不得通过临时修改生产代码绕过门禁。

## 5. 实施与测试门禁

开发过程中必须保持单一目的的短分支和可回退提交。跨模块任务应按依赖顺序拆分为可独立验证的子任务。

每个任务至少执行以下检查：

1. 变更范围检查：确认所有修改文件属于当前任务。
2. 契约检查：确认代码、测试、文档和配置使用同一版本契约。
3. 聚焦测试：覆盖正常、异常和关键边界场景。
4. 质量检查：执行项目规定的类型、格式、静态检查和依赖检查。
5. 隔离验证：在任务级环境验证数据库、消息、服务依赖和权限行为。
6. 回归验证：确认基线问题与本次新增问题分别记录。

测试失败时必须先保存失败命令、版本、输入分类、实际结果和失败层级，再决定修复代码、修复测试、修复数据或标记环境阻塞。不得只修改断言使测试通过。

### 5.1 重测判定：先问“什么变了”

测试结果不是一句“现在能不能用”，而是对下面这组条件的记录：`Issue + 契约版本 + 完整 commit + 测试命令 + 输入/fixture + 运行环境和依赖`。这组条件全部没有变化时，原证据仍然是同一次测试；只为得到一个新时间戳而重跑，不能增加可信度。

| 发生了什么 | 应做什么 | 结果如何记录 |
| --- | --- | --- |
| 完整 commit、命令、输入、环境和依赖都没变 | 不重复执行，复用原回执 | 标记“条件未变，沿用证据”，并保留原证据位置 |
| 产品代码或配置改变 | 先跑改动直接影响的聚焦测试，再跑受影响模块回归 | 新回执同时写旧基线、新 commit 和变化范围 |
| 测试脚本、断言或 fixture 改变 | 重新确认测试本身有效，再做独立验证 | 不能把新测试通过说成旧产品已经修好 |
| 数据库、Broker、依赖或权限环境修复 | 只重跑之前被环境挡住的层 | 原结论保持 `BLOCKED`，新结论另记，不能改写历史 |
| API、数据库、MQTT 或外部设备契约改变 | 先评审影响并生成新契约版本，再重新设计测试 | 旧证据只证明旧契约，不证明新契约 |
| 测试基线或候选 commit 改变 | 将旧结果保留为历史结果，按新基线重新验证 | 必须同时记录旧 SHA、新 SHA 和更换原因 |

连续两次失败但没有新的代码、数据、环境或契约证据时，暂停重跑，先做失败归因。`BLOCKED` 表示前置条件没有准备好，不等于产品 `FAIL`；健康检查通过也不等于业务验收通过。

### 5.2 需求到证据的最小追踪链

每个 Issue 或测试任务都必须能沿着下面的链条走完：

```text
Issue → 契约版本 → 设计/实现 commit → 测试编号与命令 → 环境/输入 → 实际结果 → 证据 → 验收人
```

回执至少保留以下字段：

| 字段 | 要回答的问题 |
| --- | --- |
| Issue | 要解决哪个问题，范围和非目标是什么？ |
| 契约版本 | API、数据库、MQTT 或外部设备的规则是哪一版？ |
| 完整 commit | 测的到底是哪一份代码？ |
| 测试编号与命令 | 谁可以用什么步骤复现？ |
| 环境与输入 | 用了哪个隔离环境、依赖、数据库和测试数据？ |
| 实际结果与归因 | 看到了什么，属于代码、测试、数据还是环境问题？ |
| 证据与验收 | 证据在哪里，谁确认了业务结果？ |

链条中有一项缺失时，任务只能保持 `PARTIAL`、`BLOCKED` 或 `NOT_VERIFIED`，不能写成“已完成”。

## 6. 隔离与安全门禁

任务级验证必须遵守以下要求：

- 使用独立项目名、网络、容器、卷、数据库、日志和临时凭据。
- 凭据遵循最小权限、任务级、可撤销和不写入普通日志原则。
- 不读取、复制或输出稳定环境凭据。
- 不连接或修改生产数据库、生产 Broker、真实设备和共享测试数据库，除非完成单独授权和变更审批。
- 不使用固定宿主机 IP 或依赖个人机器的隐式环境变量。
- 健康检查必须检查当前任务配置，不得写死其他环境的数据库名、用户名或端口。
- 测试结束后停止任务级进程和容器，撤销临时凭据，并保留必要的回滚材料和证据。

## 7. 验收证据要求

每个任务的回执至少包含：

- Issue、分支和完整 commit。
- 变更文件清单。
- 基线版本和依赖版本。
- 测试及检查命令、结果和失败数量。
- 基线已有问题与本次新增问题的区分。
- 隔离环境、数据库迁移、消息投递和权限验证结果（如适用）。
- 未部署、未合并、未验收等边界。
- 阻塞、风险、回滚方式和下一步。
- 脱敏后的日志或证据位置。

证据不得包含密码、Token、证书、明文连接串、客户数据、完整 JWT、敏感 payload 或不必要的敏感堆栈。

## 8. 完成定义（Definition of Done）

任务只有在满足对应层级后才能使用对应状态：

| 层级 | 必备条件 |
| --- | --- |
| 代码完成 | 代码实现完成，工作树可回读，存在局部提交 |
| 开发完成 | 聚焦测试、质量检查、审查和 Issue 回执完成 |
| 可交付 | 隔离环境运行通过，迁移、配置、权限、监控和回滚路径可复核 |
| 正式验收 | 指定验收人确认业务结果，并形成验收记录或受控标签 |

任何缺失条件必须明确标记为 `BLOCKED`、`PARTIAL` 或 `NOT_VERIFIED`，不能推断为通过。

## 9. 开发准备回执模板

开发线程开始前，应在 Issue 或任务回执中填写：

```text
状态：NOT_READY / IN_PROGRESS
需求范围：
非目标：
当前基线：
追踪关系：Issue → 契约版本 → 完整 commit → 测试编号 → 证据 → 验收人
重测原因：无变化复用 / 代码变化 / 测试或数据变化 / 环境修复 / 契约变化 / 基线变化
接口与数据契约：
测试数据及预期结果：
工具与运行环境：
任务级资源边界：
验收命令和最小通过证据：
已知阻塞和风险：
允许执行的动作：
明确禁止触碰的资源：
```

## 10. 例外管理

无法满足门禁时，负责人必须在 Issue 或 PR 中说明：未满足项、原因、影响、替代控制、批准人和失效时间。例外不应成为绕过稳定环境、安全或验收要求的长期方式。
