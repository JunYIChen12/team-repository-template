# 仓库管理与协作总规范

版本：`v1.0.0`

## 1. 目的与适用范围

本规范用于保护默认分支质量、降低多人协作的信息损失，并让需求、修改、审查和发布过程可以追溯。采用本规范的项目应在 README 中声明所采用的版本及中心链接。

## 2. 角色与责任

| 角色 | 主要责任 |
| --- | --- |
| 仓库所有者 | 权限、规则集、安全、归档和紧急处置 |
| 项目负责人 | 优先级、范围、验收标准和发布决策 |
| 代码负责人 | 对指定目录或模块进行专业审查 |
| 贡献者 | 实现、自测、说明影响并响应审查 |
| 审查者 | 检查正确性、风险、可维护性和验证证据 |

权限遵循最小够用原则。日常开发不应依赖管理员权限，离开项目的成员应及时移除访问权限。

## 3. Issue 与任务

非简单文字修正应先有 Issue 或其他可追溯任务。任务至少包含：背景、目标、范围、非目标、验收标准和负责人。一个 Issue 应尽量对应一个可以独立验收的结果。

## 4. 分支

- `main` 是默认分支并始终保持可交付。
- 禁止直接向 `main` 推送、强制推送或删除 `main`。
- 每项任务使用独立短期分支，不在一个分支混入无关变更。
- 开始工作前从最新 `main` 创建分支，合并后删除分支。
- 只有确实需要长期维护多个版本时，才引入长期发布分支。

## 5. Commit

Commit 应小而完整，信息能够说明变化目的。不得提交凭据、生成物、个人环境文件、大型无关二进制文件或未经授权的数据。需要拆分和回滚的变化不应塞进同一个提交。

## 6. Pull Request

所有进入 `main` 的变化必须通过 PR。PR 应保持单一目的并包含：背景、变更摘要、验证证据、风险、回滚方式和关联 Issue。未完成但需要讨论时使用 Draft PR。

超大 PR 难以有效审查。可以按“基础结构—核心逻辑—接入验证”拆成多个保持可运行的 PR。

## 7. 审查与批准

- 普通改动至少需要一名非作者成员批准。
- 涉及安全、权限、数据迁移、生产部署和公共接口的改动，需要相应代码负责人批准。
- 作者必须回应并解决全部有效审查意见。
- 审查者提出阻塞意见时应说明风险和解除条件。
- 作者新增实质性修改后，旧批准可以按项目风险要求失效并重新审查。

## 8. 自动检查与合并

项目具备 CI 后，构建、测试、静态检查和必要的安全检查必须通过。不得通过关闭检查、删除测试或绕过规则掩盖失败。

默认使用 Squash Merge，使一个 PR 在 `main` 上对应一个可回退的提交。PR 标题应能作为最终提交信息。合并完成后删除短期分支。

## 9. 发布与回滚

发布必须能够对应到明确的 Commit 或 Tag，并记录版本变化。高风险变化应在合并前说明回滚路径、数据兼容性和负责人。回滚应通过新的 PR 或受控的紧急流程完成，不改写 `main` 历史。

## 10. 安全与敏感信息

安全事件按[安全策略](../SECURITY.md)处理。任何人发现凭据泄露都应立即通知负责人并轮换凭据，不能只删除当前文件。依赖漏洞、自动化权限和第三方 Action 应纳入项目日常检查。

## 11. 紧急变更

生产事故允许缩短流程，但不能取消追溯：

1. 明确事故负责人、影响和临时方案。
2. 至少由另一人快速复核高风险操作。
3. 保留变更记录并验证结果。
4. 事故稳定后补齐 Issue、PR、测试和复盘。

紧急流程不能用于规避普通审查。

## 12. 例外与规范更新

需要例外时，应在 Issue 或 PR 中写明原因、风险、批准人和失效时间。规范修改必须通过 PR，并更新 `CHANGELOG.md`。重大不兼容变化发布新的主版本，由项目负责人决定升级时间。
