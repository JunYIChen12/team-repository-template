# 单设备从零配置到数据验收规范

版本：V1.1
编制日期：2026-08-27
适用对象：不熟悉仓库代码、但能使用 UI、PowerShell 和 Node-RED 的实施/测试人员  
适用范围：一台隔离设备从点表/业务输入到平台接收、UI 最新值和历史查询的完整闭环

> 本文是执行规范，不是某一台设备的配置结果。所有尖括号内容都是占位符，必须由业务输入、UI 回读或版本总账填写；不能凭经验补齐。

## 1. 目标和总原则

目标是让陌生测试人员可以在不碰正式数据的前提下，完成并证明以下闭环：

```text
点表/业务输入
  -> 平台设备类型与物模型
  -> 网关与受控身份
  -> Topic 与消息规则
  -> 设备绑定
  -> Node-RED 只读采集与标准上报
  -> 平台接收、校验、保存
  -> UI 最新值与历史查询
  -> 证据、问题归因和可回滚收束
```

执行原则：

1. 先锁定版本和资源归属，再进行任何写入或连接。
2. 缺少点表字段、业务口径或权限时写“待确认/BLOCKED”，不得猜测。
3. UI 是最终验收入口；后台/API/数据库只能辅助定位或准备隔离数据。
4. Node-RED、PLC、网络和凭据交接问题单独归因，不自动写成平台缺陷。
5. 每一步都只能有三种动作：通过后继续、阻塞后转交、失败后按回滚规则处理。
6. 不受影响的步骤可以继续，但必须记录依赖和未完成边界。

## 2. 规范和版本绑定

执行任务前，在任务回执中记录本次实际读取到的规范版本与完整 SHA。以下是本规范需要一并读取的规则类别；采用时填写实际来源和完整 SHA，不得把某个项目的本地路径或运行值写进本模板：

| 规范类别 | 用途 | 采用时填写的来源/完整 SHA |
|---|---|---|
| 项目与资源边界 | 目录、资源归属、版本键、清理和证据命名 | `<规范来源> @ <完整 SHA>` |
| IoT 测试体系 | 测试模型、任务字段、证据和 L1-L8 归因 | `<规范来源> @ <完整 SHA>` |
| 候选环境交付契约 | 候选版本、依赖、镜像、端口、迁移、Secret、回滚和超时门禁 | [`docs/iot/候选环境交付契约.md`](../iot/候选环境交付契约.md) @ `<完整 SHA>` |
| 故障排查顺序 | 现象、平台、环境、采集和联合问题的判定顺序 | `<规范来源> @ <完整 SHA>` |
| 环境隔离规则 | 环境、数据库、网络、凭据和证据隔离 | `<规范来源> @ <完整 SHA>` |

如果任务指定了更新版本，更新版本优先；旧版本不得被覆盖。文档和证据必须绑定：

```text
完整 Git SHA + worktree 绝对路径 + 环境编码 + 设备编码 + 证据编号/SHA-256
```

## 3. 四种证据等级

| 等级 | 含义 | 可以证明什么 | 不能证明什么 |
|---|---|---|---|
| UI PASS | 通过正式 UI 入口观察并回读 | 操作入口存在、字段显示、业务用户可见结果 | 后台数据一定正确、其他环境一定可用 |
| 后台旁路 | API/CLI/DB 只读或隔离写入辅助 | 对象准备、字段详情、错误定位、隔离夹具数据 | UI 闭环已通过、生产可用 |
| 静态检查 | 代码、schema、Compose、文档或迁移记录 | 设计入口、字段约束、责任边界和预期行为 | 运行时连接、真实数据、性能和业务结果 |
| 真实运行验收 | 在授权隔离环境实际运行并观察结果 | 端到端行为、时间推进、消费/入库和业务结果 | 未覆盖的设备、版本或生产环境 |

结论必须写明证据等级。`healthy` 只能证明相应 healthcheck 的范围，不等于业务入库；“已登记”不等于“已迁移”；“接口返回 200”不等于 UI 验收通过。

## 4. 八层归因和责任边界

| 层 | 名称 | 主要责任 |
|---|---|---|
| L1 | 资源与配置管理 | 设备、网关、点位、物模型、Topic、版本和启用状态 |
| L2 | 设备接入与采集任务 | 协议、轮询、连接、超时、重试和采集任务 |
| L3 | 可靠采集与数据质量 | 时间、重复、乱序、缺失、延迟、补传和质量 |
| L4 | 数据存储与查询 | 原始值、标准值、latest/history、分页和时间范围 |
| L5 | 数据处理、事件与计算 | 单位标准化、事件、窗口、累计差值和计算版本 |
| L6 | 业务上下文关联 | 工单、批次、产品、工序和业务事件关联 |
| L7 | 北向数据服务 | REST、MQTT、确认、重试、去重、限流和契约 |
| L8 | 平台治理、安全与运维 | 健康、审计、权限、Secret、备份、恢复和回滚 |

责任分类统一使用：`PLATFORM`、`NODERED`、`OPERATION`、`ENVIRONMENT`、`EXTERNAL`、`JOINT`。

- Node-RED 负责 PLC/Modbus/串口/OPC-UA 读取、解码、断网缓冲、补传和标准报文发送；平台不托管现场采集运行时。
- PLC 只允许 FC01/FC03 只读；禁止写 PLC。
- 禁止发布生产 MQTT 或猜测凭据。测试消息只能使用隔离 Broker、隔离 Topic 和受控身份。
- 平台负责 MQTT 接收、Topic 规则、物模型校验、入库、查询、计算和治理。

## 5. 总体执行顺序

```text
0 版本与资源门禁
  -> 1 输入契约
  -> 2 设备类型与物模型
  -> 3 网关与身份
  -> 4 Topic 与消息规则
  -> 5 设备与绑定
  -> 6 Node-RED 采集层前置
  -> 7 报文与首接入
  -> 8 平台接收可观察性
  -> 9 UI 验收
  -> 10 历史与追溯
  -> 11 重启恢复
  -> 12 证据、问题与收束
```

必须串行：版本门禁、数据库迁移、bootstrap、业务配置写入、Secret 导入、服务重启、流量切换和回滚。  
可以并行：Git/Compose/镜像/端口/磁盘静态检查、点表阅读、Node-RED flow 静态审查和证据模板准备。

## 6. 阶段 0：版本与资源门禁

**责任方**：环境负责人；实施人员协助提供业务设备编码。  
**前置条件**：目标是隔离环境，且已明确不使用 accepted、旧 candidate 或生产资源。

### 动作

Windows PowerShell 只读检查：

```powershell
Get-Location
Get-PSDrive -Name C,D | Select-Object Name,Free,Used
git -C <worktree> rev-parse --show-toplevel
git -C <worktree> rev-parse HEAD
git -C <worktree> status --short
git -C <worktree> worktree list
docker ps --format '{{.Names}}|{{.Status}}|{{.Ports}}'
docker volume ls
docker network ls
Get-NetTCPConnection -State Listen
```

填写并锁定：

```text
Git 分支/标签：<branch-or-tag>
Git 完整 SHA：<40-char-sha>
worktree：<绝对路径>
Compose 路径/SHA-256：<...>
镜像名称/digest：<...>
环境编码：<环境类型_版本短SHA_用途_日期>
数据库 owner/路径或 volume：<...>
Node-RED 目录：<...>
证据目录：D:\003_workspace\06_证据与验收\<日期>_<版本短SHA>
回滚路径：<accepted/备份登记>
```

### 可观察输出和通过标准

- 当前目录属于目标项目；Git SHA、worktree、Compose、镜像、迁移账本和环境编码彼此一致。
- 端口没有被另一套环境占用；磁盘空间满足门槛，D 盘优先存放运行数据和证据。
- Docker、数据库、Node-RED 和证据目录的 owner、用途、清理边界明确。

### 失败决策树

```text
版本/环境无法唯一绑定？ -> BLOCKED，补版本总账。
发现使用正式资源或 accepted/candidate 混用？ -> 停止，转环境负责人隔离。
端口被占用？ -> 记录占用者，不强杀；改用已批准隔离端口或 BLOCKED。
磁盘低于门槛/临时空间快速下降？ -> 停止高成本动作，先做资源取证。
Docker 不可用但本任务仅文档/静态检查？ -> 可继续静态部分，运行步骤 BLOCKED。
```

### 回滚/继续规则

此阶段只读，无业务回滚。门禁不通过时只能补齐登记或换隔离环境，不能跳过并声称后续通过。

## 7. 阶段 1：输入契约

**责任方**：业务/点表负责人提供；平台负责人审核；Node-RED 仅确认可采集性。  
**前置条件**：设备业务名称、稳定设备编码和点表来源已确认。

### 必填输入表

| 字段 | 示例占位符 | 规则 |
|---|---|---|
| 设备中文名/稳定编码 | `<回流焊设备>` / `<PLC-xxx>` | 编码稳定且唯一 |
| 设备类型 | `<type-code>` | 不用显示名称代替 |
| 控制器地址 | `<IP/hostname>` | 由现场确认，不猜 |
| 端口/站号/协议 | `<502>/<unitId>/<Modbus TCP>` | 缺一项即待确认 |
| 点位业务名/identifier | `<轨道1出板累计计数>` / `<track1OutputCount>` | identifier 稳定唯一 |
| PLC 地址/完整 Modbus 地址 | `<D37>/<...>` | 同时记录 0 基/1 基口径 |
| 功能码/偏移/数量 | `<FC03>/<offset>/<quantity>` | 只允许 FC01/FC03 只读 |
| 数据类型/字节序 | `<INT16>/<AB>` | 不从数值外观猜类型 |
| 缩放/单位 | `<0.1>/<块>` | 原始单位和平台单位分开 |
| 枚举/范围 | `<enum/range or none>` | 空值写“无”而非省略 |
| 采集周期/心跳 | `<period/heartbeat>` | 用于新鲜度门槛 |
| 是否累计/可清零 | `<yes/no/reset event>` | 清零必须可审计 |

### 可观察输出和通过标准

- 点表工作表名、行号、文件 SHA-256 已记录。
- 每个点位所有必填列都有值；缺失或冲突字段单独列出，不使用默认值掩盖。
- 明确原始值、标准化值和平台物模型值的责任归属，避免 Node-RED 与平台重复缩放。

### 失败决策树

```text
地址/功能码/类型/单位缺失？ -> BLOCKED，回点表负责人确认。
同一地址存在多个单位/类型？ -> BLOCKED，保留冲突，不选“看起来合理”的值。
需要写 PLC 才能确认？ -> 禁止，转 EXTERNAL/OPERATION 说明。
点表完整但平台字段尚未配置？ -> 进入阶段 2，归 PLATFORM 前置。
```

### 回滚/继续规则

输入契约未冻结前可继续做静态 schema 审查，但不得创建正式物模型或发送首条消息。冻结后的点表变更必须产生新版本和差异记录。

## 8. 阶段 2：设备类型与物模型

**责任方**：平台实施/UI；业务负责人确认中文名、单位和必填口径。  
**前置条件**：阶段 1 输入契约已冻结。

### 配置字段

```text
设备类型 identifier/name：<...>
属性 identifier/name：<...>
dataType：int | float | string | bool | enum | datetime
unit：<...>（布尔默认无单位，除非业务明确）
required：true/false
status：enabled/disabled
enumMap：<...>
counterResetEnabled：true/false
description：<业务解释>
```

事件对象不要塞入标量属性模型。若平台版本尚未支持 `event_post` 入站，事件应保持单独的待办/阻塞状态，不能伪装成属性。

### 动作与通过标准

1. UI 新建或打开设备类型，逐项添加属性。
2. 保存后关闭并重新打开页面，回读 identifier、name、类型、单位、必填、启用状态。
3. 对一项合法样例和一项非法类型样例做只读/隔离验证。
4. 记录 UI PASS；后台回读只能作为旁证。

通过条件：

- UI 能显示并回读全部字段；属性类型与输入契约一致。
- 可选属性在缺失时不会被误判为必填缺失；禁用属性行为可解释。
- 缩放不在物模型层重复执行；单位差异有记录。

### 失败决策树

```text
页面保存失败且请求字段与 schema 不一致？ -> OPERATION/PLATFORM 候选，保存请求与错误码待补。
类型下拉没有业务所需类型？ -> PLATFORM UI 缺口候选，不用后台绕过替代 UI 验收。
后端已保存但 UI 回读不一致？ -> PLATFORM/UI，保留后台旁路证据并阻塞 UI PASS。
物模型值不匹配但点表本身未冻结？ -> OPERATION/业务输入 BLOCKED。
```

### 回滚/继续规则

保存前保留配置导出或截图；失败时不重复试错写入。可以继续阶段 3 的凭据来源核对，但不能启用规则接收未定义字段。

## 9. 阶段 3：网关与身份

**责任方**：平台安全/环境负责人；实施人员只操作 UI 中授权入口。  
**前置条件**：设备类型和网关归属已确定。

### 受控来源和注入

凭据来源只能是平台正式生成/轮换入口、受控 Secret、或已批准的密钥管理工具。一次性密钥只在创建/轮换后现场保存到受控存储；不得粘贴到普通文档、日志、Issue 或截图。

登记非敏感字段：

```text
gatewayCode/id：<...>
ownerType/ownerId：<...>
身份状态：<generated/imported/active/disabled>
Secret 存储引用：<secret-name-or-vault-ref>
ACL 指纹/范围：<脱敏摘要>
哈希/版本：<hash-or-version>
导入时间/操作者：<...>
```

### 动作与通过标准

1. UI 创建或回读网关身份，不复制密钥到回执。
2. 将身份通过受控 Secret 机制导入隔离 runtime。
3. 回读 runtime 已加载身份（只记“已加载/未加载”）。
4. 以单台设备的最小权限检查 ACL 是否覆盖完整 Topic，并拒绝另一设备 Topic。

### 失败决策树

```text
身份已生成但 runtime 未导入？ -> 运行时前置 BLOCKED。
ACL 只写短通配符且 Topic 层级未核对？ -> 权限风险 BLOCKED。
规则停用导致无 ACL？ -> 先确认是否应启用；不归 Node-RED。
密钥无法安全保存或已泄露？ -> 停止使用，按安全负责人轮换并登记，不回显旧值。
认证失败但 ACL/规则均正确？ -> 分别核对 Broker、runtime 注入和客户端配置，不直接定性平台。
```

### 回滚/继续规则

凭据导入失败不得把密钥写入临时文件。可回滚到上一份受控 Secret 引用；若无法证明旧密钥仍有效，必须重新走轮换和回读门禁。

## 10. 阶段 4：Topic 与消息规则

**责任方**：平台实施；业务负责人确认命名；Node-RED 只按冻结契约发送。  
**前置条件**：设备编码、网关、物模型和身份已回读。

### Topic/规则契约模板

```text
规则 code：<稳定唯一编码>
规则 name：<中文业务名称>
direction：upstream
messageType：property_post | event_post | status_post
topicPattern：<完整模板>
expressionType：template | exact | mqtt_wildcard
deviceCodeSource：topic | payload | both
deviceCodePath：<若适用>
payloadMode：standard | root_properties | mapped
timestampSourcePath：<若适用>
qos：<0/1/2，以平台契约为准>
priority：<...>
status：enabled/disabled
gatewayId/deviceTypeId：<...>
historyMode/heartbeat：<...>
```

标准属性报文占位：

```json
{
  "deviceCode": "<稳定设备编码>",
  "timestamp": "<ISO-8601 with timezone>",
  "messageId": "<source-stable-id>",
  "traceId": "<request-trace-id>",
  "properties": {
    "<identifier>": "<value>"
  }
}
```

### 动作与通过标准

1. 先执行 dry-run/只读唯一性检查：`code` 全局唯一，启用规则的方向、消息类型和 Topic 模式不冲突。
2. 核对 `gatewayId` 与设备网关一致，确认 ACL 能覆盖完整 Topic。
3. 写入规则后 UI 关闭重开并回读所有字段。
4. 属性和事件规则分开登记；如果目标版本没有事件入站支持，事件规则不得启用。

### 失败决策树

```text
code 或启用模式冲突？ -> 不写入，调整业务命名或停用旧规则后重新确认。
Topic 能匹配但设备身份来源冲突？ -> BLOCKED，修正 payload/topic 契约。
网关不同却共用无法授权的规则？ -> 平台权限风险，确认独立模式或统一网关。
event_post 只能创建但运行会拒绝？ -> PLATFORM BLOCKED，不交给 Node-RED 绕过。
UI 回读缺字段？ -> UI 验收失败，后台旁路不能替代。
```

### 回滚/继续规则

写入前保存旧规则摘要和启用状态。失败时只恢复旧规则，不删除历史接入日志；任何 Topic 改名都必须保留旧规则停用记录。

## 11. 阶段 5：设备与绑定

**责任方**：平台实施/UI。  
**前置条件**：设备类型、网关、Topic 规则已冻结。

### 动作与观察

1. 创建/回读设备 `code/name/deviceTypeId/gatewayId/enabled`。
2. 确认设备编码与 Topic 中的 `{deviceCode}` 一致。
3. 确认设备只绑定一台目标网关和一个目标环境。
4. UI 关闭重开，确认设备状态和绑定关系持久化。

### 通过标准

- 设备、网关、设备类型和规则可以从 UI 互相回链。
- 设备启用状态、在线状态和最后数据时间字段可被观察。
- 不存在同编码跨环境或同设备多网关歧义。

### 失败决策树

```text
设备编码冲突？ -> L1 BLOCKED，业务确认稳定键。
设备类型/网关不存在？ -> 回到阶段 2/3，不创建临时替代对象。
绑定保存成功但回读不一致？ -> PLATFORM/UI 候选，保留读回证据。
设备未启用？ -> OPERATION 前置；不发送首条测试消息。
```

## 12. 阶段 6：Node-RED 采集层前置

**责任方**：Node-RED/现场采集专家；平台人员只核对输入契约。  
**前置条件**：阶段 1 点表和阶段 4 Topic 已冻结，且明确为隔离采集。

### Flow 最小检查

```text
Flow 来源/版本：<来源路径或仓库 ref>
Flow SHA-256：<...>
manifest/environment：<...>
Tab：<设备/用途>
Modbus host/port/unitId：<由登记 profile 提供>
功能码：仅 FC01/FC03
地址/offset/quantity：<逐点登记>
周期/超时/reconnect：<...>
decode/scale/unit：<责任方>
Topic/deviceCode/messageId/timestamp：<冻结契约>
凭据引用：<受控 Secret 名称，不写值>
```

### 动作与通过标准

1. 只读审查 Flow SHA、manifest、Tab 和关键节点引用，确认没有写 PLC 节点（FC05/06/15/16）。
2. 确认每台设备使用登记 profile 的 host/port/unitId、地址、功能码和数量。
3. 单台加载或重载 Flow，确认凭据从 Node-RED credential store/受控 Secret 获取。
4. 观察标准报文：设备编码、事件时间、属性标识符、单位/缩放和稳定 messageId。
5. 断线/恢复、重复、乱序和补传仅在授权隔离夹具中执行。

### 通过标准

- Modbus 只读请求与点表一致，采集周期和超时可观察。
- Flow 发布标准报文到隔离 Topic，未携带明文凭据。
- 断线恢复和补传保留原始采样时间；重发保持同一 messageId（若契约要求）。
- 单台重载不影响其他设备。

### 失败决策树

```text
PLC 不可达/ECONNREFUSED？ -> NODERED/EXTERNAL/ENVIRONMENT，先修网络或现场条件。
节点缺失、Flow SHA 漂移、clientId/ACL 错？ -> NODERED/配置，不能写成平台接收缺陷。
读取正常但标准报文不符合契约？ -> NODERED/JOINT，先修采集层输出。
报文契约正确但平台拒收？ -> 进入阶段 8，收集平台错误码后再归因。
发现写 PLC 节点或生产 Topic？ -> 立即停止，按安全流程回滚并报告。
```

### 回滚/继续规则

Node-RED 问题不得通过修改平台物模型掩盖。保留原 Flow/manifest SHA，回滚只针对隔离采集配置；平台静态阶段仍可继续，但正式接入必须 BLOCKED。

## 13. 阶段 7：报文与首接入

**责任方**：平台和 Node-RED 联合；环境负责人提供隔离 Broker。  
**前置条件**：规则启用、ACL 已加载、runtime 凭据已注入、单台设备可连接。

### 首条消息模板

```json
{
  "deviceCode": "<目标设备编码>",
  "timestamp": "<带时区事件时间>",
  "messageId": "<稳定消息ID>",
  "traceId": "<可选追踪ID>",
  "properties": {
    "<已启用identifier>": <合法值>
  }
}
```

### 动作与通过标准

1. 先发送一条单属性、合法类型的隔离消息。
2. 记录发送端非敏感 clientId、Topic、messageId、timestamp 和 payload 字段名。
3. 不重复发送密钥；同一消息的重试只复用稳定 messageId。
4. 观察 Broker PUBACK/连接结果和平台接入日志。

通过标准：认证成功、Topic 命中唯一规则、设备身份一致、物模型校验成功，且能继续阶段 8。

### 失败决策树

```text
认证失败？ -> 核对 runtime Secret、ACL、Broker 和 clientId，暂不判平台。
Topic 未命中？ -> 核对最终字符串、通配符层级、规则状态。
设备身份冲突？ -> 停止发送，修正 deviceCodeSource 或 payload。
物模型类型/必填失败？ -> 对照阶段 1/2，确认是报文还是平台 schema。
消息成功但无入库？ -> 进入阶段 8，查 ingestion 日志和数据库时间推进。
```

## 14. 阶段 8：平台接收可观察性

**责任方**：平台/环境；Node-RED 只提供发送事实。  
**前置条件**：首条消息的 messageId、Topic 和时间已记录。

### 必须观察字段

```text
ingestionLogId：<...>
status：pending/success/failed
errorCode/errorMessage：<脱敏>
topic/topicRuleId/ruleCode：<...>
deviceId/deviceCode/gatewayId：<...>
clientId：<非敏感值>
messageId/traceId：<...>
occurredAt/receivedAt/processedAt：<...>
normalizedPayload/rawPayload：只记录字段摘要，不写密钥
historyWritten/latestUpdated：<...>
processingLatencyMs：<...>
```

### 通过标准

- 合法消息状态为 success，规则、设备、网关和来源一致。
- `occurredAt` 来自事件/采样时间；`receivedAt` 单独用于接收和新鲜度判断。
- latest/history 至少出现目标属性，值、类型、单位和质量可解释。
- 非法类型、未知属性、缺必填字段会失败并记录明确原因。
- 重复消息的实际行为与已冻结幂等契约一致；未冻结则写“待确认”。

### 失败决策树

```text
无 ingestion log？ -> 先查 Broker 消费/订阅和平台连接，再判断环境或平台。
有 log 但 topic_not_matched？ -> Topic/规则配置边界。
有 log 但物模型失败？ -> 报文类型、字段类型、必填和物模型契约。
log 成功但 history/latest 不变？ -> PLATFORM/L4 候选，采集输入已排除后再建 Issue。
数据库有数据但 UI 不显示？ -> 进入阶段 9，不能用后台结果替代 UI PASS。
```

## 15. 阶段 9：UI 验收

**责任方**：UI 验收人员；平台/环境提供只读支持。  
**前置条件**：阶段 8 已有至少一条成功接入记录。

### 操作顺序

1. 登录正式 UI，确认账号角色和隔离环境标识。
2. 打开设备页，回读设备、网关、物模型、Topic 和“有新数据/最后更新时间”。
3. 连续刷新至少三次，记录值、时间、质量和页面状态。
4. 打开历史页，选择明确时间范围，检查分页、单位、质量、来源和错误提示。
5. 若有计算结果，进入计算详情/运行记录/输入摘要；后台旁路只作为辅助。
6. 记录页面截图或结构化回执，文件名按证据规范绑定版本短 SHA。

### UI PASS 标准

- 页面能显示正确业务设备中文名和稳定设备编码。
- 最新值在连续刷新中按预期推进，时间字段和单位可解释。
- 历史查询能按设备、点位和时间范围回读，结果与阶段 8 的入库事实一致。
- UI 能显示失败质量/原因或明确“无结果”，而不是静默空白。
- 不需要后台猜测、数据库直读或复制密钥才能完成上述判断。

### 失败决策树

```text
无法登录？ -> OPERATION/权限/环境前置，先补会话，不判数据平台。
页面无设备/物模型？ -> 回阶段 2/5，确认是否配置或 UI 查询缺口。
后台有数据、UI 无数据？ -> PLATFORM/UI 候选，保留 UI 证据，不能标 PASS。
显示“有新数据”但时间和值不推进？ -> 回阶段 8 查入库，再区分平台/采集。
历史有记录但无结果？ -> 记录质量/窗口语义，不能把空值自动判筛选问题。
```

### 回滚/继续规则

UI 验收失败不通过后台改写结果来“修正截图”。可继续只读日志和 API 诊断；任何配置修改必须重新从受控 UI 流程开始并生成新证据。

## 16. 阶段 10：历史与追溯

**责任方**：平台/UI；业务负责人解释单位、质量和计算口径。  
**前置条件**：至少一个成功入库样本和一个可查询时间范围。

### 追溯链

```text
业务结果/属性值
  -> 设备编码 + 点位 identifier
  -> occurredAt/receivedAt
  -> rawValue + normalizedValue + unit + dataType
  -> ingestionLog(messageId/traceId/topic/rule)
  -> 规则版本/物模型版本/计算版本
  -> quality + reason + revision
```

### 通过标准

- 原始值、标准值、单位和质量字段可区分。
- 同一结果可以回链设备、点位、时间、来源消息和规则版本。
- 迟到数据或修订使用新 revision，不覆盖历史事实。
- 计算结果的输入摘要、窗口边界、规则版本和运行记录可定位。
- `pcs`/“块”等单位差异有业务解释，不能静默换算。

### 失败决策树

```text
只有数字、没有输入/来源？ -> PLATFORM/L4-L5 追溯缺口候选。
有输入但时间或版本缺失？ -> 记录 PARTIAL，补证后再定性。
单位冲突来自点表？ -> 业务输入/OPERATION，保留冲突；不是立即平台 Bug。
质量为 BAD/no_result？ -> 按质量原因解释，不把无结果当 UI 丢失。
```

## 17. 阶段 11：重启恢复

**责任方**：环境/运维；平台和 Node-RED 分别确认自身边界。  
**前置条件**：阶段 0 版本总账、数据库备份、Secret 引用、Node-RED 持久化和回滚路径齐全。

### 固定契约

```text
Compose 文件/服务名：<...>
宿主端口/容器端口：<...>
数据库路径/Volume owner：<...>
迁移账本：<canonical ledger>
Secret 引用：<受控名称，不写值>
EMQX data/config：<持久化路径>
Node-RED data/flow/credential store：<独立路径>
health/readiness 检查：<分层端点>
回滚版本/备份：<...>
```

### 动作与通过标准

1. 重启前保存 manifest、数据库 dump/备份、Compose 和镜像指纹。
2. 只使用已批准的 Compose 入口和既有 Volume；不得用空卷或 `down -v` 代替恢复验证。
3. 按顺序等待数据库、迁移、bootstrap、API、EMQX auth、Ingester 和 Web readiness。
4. Secret 通过受控方式注入并验证“已加载”，不输出值。
5. 重新执行单台属性接入和 UI 回读；对比重启前后 messageId、最新时间和历史记录。

5 分钟目标是预算，不是默认事实。建议记录：版本预检 30 秒、基础设施 60 秒、迁移/bootstrap 60 秒、API/认证 60 秒、Ingester 45 秒、Web/UI 45 秒；超时必须记录具体层级。

### 失败决策树

```text
迁移失败？ -> 停止流量切换，保留 dump/账本，按迁移回滚流程处理。
Secret 未加载？ -> 阻塞，不生成新密钥试错；核对受控注入和 owner。
API healthy 但 MQTT 未订阅/无消费？ -> 业务 readiness 未通过，不能写“平台恢复”。
Ingester 恢复但 UI 不推进？ -> 按阶段 8/9 继续定位。
Node-RED 未恢复但平台健康？ -> NODERED/EXTERNAL，不把平台标为已验收。
超出 5 分钟？ -> 记录瓶颈层，保留环境，不自动重启循环。
```

### 回滚/继续规则

回滚优先恢复应用、Compose、Secret 引用和网络，不删除数据库或业务 Volume。只有备份可恢复、迁移账本一致、服务分层 ready 且 UI 重新通过，才可结束恢复窗口。

| 两层同时影响且无法拆分 | JOINT | 先拆分证据，再分别归因 |

### 收束清单

- [ ] 首条消息、接入日志、latest/history 和 UI 证据均有记录。
- [ ] UI PASS 与后台旁路、静态检查、真实运行验收分开标记。

- [ ] 未把“服务健康”写成“业务验收”，未把“登记”写成“迁移”。
- [ ] 未输出密码、Token、证书、授权头或私密连接串。
- [ ] 临时资源 owner、用途和清理条件已记录；Unknown 不删除。

## 23. 平台接入契约与重复检查模板

本节是与具体设备、项目和环境无关的可复制模板。每次接入只填写尖括号占位符；空缺写“待确认”，不凭经验补齐。

### 23.1 身份映射契约

| 检查项 | 要求 | 填写值 |
|---|---|---|
| 原始设备标识字段 | 明确来源字段、格式和大小写规则 | `<sourceDeviceId 字段/格式>` |
| 平台稳定设备编码 | 明确唯一编码规则和合法字符 | `<platformDeviceCode 规则>` |
| 映射表 | 显式记录 `sourceDeviceId -> platformDeviceCode`，一对一且可版本化 | `<映射表版本/证据>` |
| 原始标识保留 | 原始标识只能作为诊断元数据，不能替代平台稳定键 | `<保留字段/位置>` |
| 未知标识处理 | 拒绝或进入隔离错误队列，不自动猜测或创建新设备 | `<reject/quarantine 规则>` |

通过标准：同一原始标识始终得到同一平台编码；未知标识不会串到其他设备；映射变更有版本和回滚记录。

### 23.2 时间字段契约

| 字段 | 业务含义 | 格式与时区 | 缺失/非法处理 |
|---|---|---|---|
| `sampledAt` | 设备或采集器实际采样时间 | RFC 3339/ISO 8601，必须含 `Z` 或明确偏移 | `<...>` |
| `occurredAt` | 事件或状态发生时间 | 同上；不得使用本地化斜杠文本 | `<...>` |
| `receivedAt` | 平台收到消息的时间 | 由平台统一生成 | `<...>` |
| `processedAt` | 平台完成校验/入库的时间 | 由平台统一生成 | `<...>` |

通过标准：采样、发生、接收、处理四种时间不混用；时间可排序、可比较；非法时间被明确拒绝或标记质量问题，不静默改写。

### 23.3 字段映射契约

| 来源路径 | 平台 identifier | 名称 | 数据类型 | 单位 | 缩放/枚举 | 必填 | 空值策略 | 质量规则 | 版本/证据 |
|---|---|---|---|---|---|---|---|---|---|
| `<source.path>` | `<identifier>` | `<中文名称>` | `<int/float/bool/string/...>` | `<unit/无>` | `<...>` | `<是/否>` | `<省略/空值/拒绝>` | `<...>` | `<...>` |

规则：元数据（身份、来源、采样时间）与业务属性分开；缩放、类型转换和单位转换只能由一个责任层执行；新增或改名必须同时更新物模型、采集 Flow 和数据契约；未定义字段不得静默丢弃。

### 23.4 Topic 与消息规则契约

| 检查项 | 要求 | 填写值 |
|---|---|---|
| 规则编码/消息类型 | 稳定唯一；属性、事件、状态通道分开 | `<ruleCode>/<messageType>` |
| Topic 模板 | 使用明确占位符，设备编码来源固定 | `<topicPattern>` |
| 身份绑定 | `deviceType/gateway/device` 绑定关系可回读 | `<绑定键>` |
| 载荷模式 | 标准字段名、版本和字段位置固定 | `<payloadMode/schemaVersion>` |
| QoS/保留/确认 | 按平台契约填写，不能默认推断 | `<qos/retain/ack>` |
| 幂等与重试 | 稳定 `messageId`、重试上限和重复处理规则明确 | `<...>` |
| 启用与回滚 | 启用前做唯一性检查，保存旧状态和回滚指纹 | `<...>` |

通过标准：最终 Topic 可由规则唯一匹配；设备身份、网关和物模型一致；非法 Topic 或未知设备不会被错误接收。

### 23.5 端口与链路契约

| 端口角色 | 监听方 | 绑定范围 | 容器/宿主映射 | 协议与帧边界 | 检查信号 |
|---|---|---|---|---|---|
| 采集输入 | `<collector/Node-RED>` | `<loopback/内网>` | `<container:host>` | `<TCP/HTTP/...>`、`<换行/长度>` | `<listener + frame count>` |
| Broker | `<broker>` | `<...>` | `<...>` | `<MQTT/TLS>` | `<connected + auth>` |
| 平台入口 | `<ingester/API>` | `<...>` | `<...>` | `<...>` | `<subscription/ready>` |

通过标准：每个端口只有一个目标 owner；监听、路由、认证和订阅均可独立观察；短连接或 TCP 状态不能单独当作业务成功/失败，必须结合完整帧和平台接收记录判断。

### 23.6 凭据引用契约

| 检查项 | 要求 | 填写值 |
|---|---|---|
| 引用名称 | 只记录 Secret/credential 的名称或引用 ID | `<secretRef>` |
| 存储位置 | 受控 Secret 或 Node-RED credential store | `<storeRef>` |
| 权限范围 | 仅允许目标 Broker、Topic 和动作 | `<ACL 摘要>` |
| 注入状态 | 记录存在、owner、权限和哈希，不读取值 | `<metadata/sha>` |
| 轮换/回滚 | 轮换前后引用可区分，旧引用保留到验收结束 | `<...>` |

禁止：把密码、Token、证书、授权头或完整连接串写入 Flow、普通 Compose 变量、日志、截图、Issue 或本模板。

### 23.7 Flow 与版本指纹契约

| 指纹 | 计算对象 | 计算方法 | 期望关系 | 填写值 |
|---|---|---|---|---|
| Git SHA | 代码/配置来源 | 完整 commit SHA | 与采用版本一致 | `<...>` |
| Flow SHA | 原始 Flow 文件字节 | 对原始字节计算 SHA-256 | 与 manifest 登记一致 | `<...>` |
| Manifest SHA | 运行清单原始字节 | 对原始字节计算 SHA-256 | 与部署记录一致 | `<...>` |
| 运行态指纹 | 实际加载 Flow/关键节点摘要 | 由运行时只读回读 | 与候选和清单一致 | `<...>` |

通过标准：哈希计算对象和编码方式明确；原始文件哈希与运行时序列化哈希分开；任何漂移都先 BLOCKED，不用“看起来一样”替代回读。

### 23.8 验收信号契约

按顺序记录下列外部可观察信号，不能用单个信号代替整条链路：

```text
采集帧完整且字段可解析
  -> Node-RED 标准化输出（身份/时间/字段/质量）
  -> Broker 连接、认证、授权和发布确认
  -> 平台规则命中与接收状态
  -> 物模型校验结果
  -> 原始/标准历史写入与 latest 推进
  -> UI 或正式查询入口回读
```

| 信号 | 通过条件 | 失败时先归因 |
|---|---|---|
| 输入帧 | 数量、边界、解析错误可解释 | `NODERED/EXTERNAL` |
| Broker | 连接、认证、授权和发布状态成功 | `NODERED/ENVIRONMENT` |
| 平台接收 | Topic/规则/设备/时间可回读 | `PLATFORM` 或前置边界 |
| 物模型 | 类型、单位、必填和质量规则通过 | `PLATFORM` 或报文契约 |
| 存储 | history/latest 值和时间推进 | `PLATFORM` |
| UI/查询 | 业务人员可见、可刷新、可按时间回读 | `PLATFORM/UI` |
