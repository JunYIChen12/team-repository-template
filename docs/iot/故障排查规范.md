# IoT 故障排查规范

## 规范身份

- 规范编号：`TROUBLESHOOT-IOT-001`
- 版本：`V1.0`
- 生效日期：`2026-08-26`
- 适用范围：IoT 平台、外部采集层、设备数据接入、计算、北向服务和本地测试环境
- 规范定位：把已有的测试、环境和启动规则串成一条可执行的故障定位路径

本文件不替代以下规范：

- [测试体系核心规则](测试体系核心规则.md)：定义测试任务、结论、证据和能力归因；
- [环境隔离规范](环境隔离规范.md)：定义环境身份、资源归属、启动门禁和凭据边界；
- [目录与编码规范](目录与编码规范.md)：定义八层目录、版本绑定和证据命名。

## 1. 目标和原则

故障排查要回答四个问题：

1. 哪一层先出现可观察异常；
2. 哪个责任边界可以被证据支持；
3. 当前能否安全绕过并继续不受影响的测试；
4. 什么证据可以证明恢复，而不是只证明进程还活着。

固定原则：

- 先确认用户能看到的现象，再逐层倒查；
- 先只读，后受控写入；迁移、配置、重启和流量切换必须串行；
- 不用 API、数据库、日志或模拟输入替代明确要求的真实 UI 验收；
- 不把 Node-RED、PLC、操作和外部依赖问题冒充平台缺陷；
- 证据不足时写 `BLOCKED` 或“尚未确认”，不得猜根因；
- 单个异常不应自动阻塞其他不相关场景，阻塞范围必须写清楚。

## 2. 故障分类

| 分类 | 含义 | 典型证据 | 处理边界 |
| --- | --- | --- | --- |
| `PLATFORM` | 平台接收、校验、存储、查询、计算、北向或治理行为不符合契约 | UI/API/运行记录在合法输入下稳定复现 | 可形成平台 Issue |
| `NODERED` | 读取、解码、边沿、序号、格式或采集 Flow 行为异常 | PLC 读值、Flow 节点、发送报文或采集层日志 | 转采集层专项，不进入平台 Issue |
| `OPERATION` | 账号、权限、页面操作、测试入口或工具使用错误 | 权限提示、参数缺失、错误入口或操作记录 | 修正操作后复测 |
| `EXTERNAL` | PLC、设备、网络、凭据提供方或北向消费端不可用 | 设备关机、网络不可达、合法凭据缺失 | 记录前置条件，不判平台失败 |
| `JOINT` | 两个或多个边界共同影响，单一责任方无法成立 | 各边界均有相关证据 | 拆分证据后再归因 |

故障分类不等于结论。结论仍使用测试体系规定的 `PASS / PARTIAL / FAIL / BLOCKED / NOT_APPLICABLE`。

## 3. 标准排查顺序

### 3.1 第一步：固定现象和范围

记录：业务对象、设备编码、发生时间、页面入口、看到的具体状态、最后成功时间、影响的点位/窗口/消费者，以及是否只影响一台设备。

禁止使用“平台坏了”“没有数据”这类未展开的结论。至少要写成：

```text
设备：中文名称（稳定键）
现象：页面显示什么，值/时间/质量/错误是什么
范围：单点、单设备、单服务、所有设备或北向输出
时间：首次观察、最后正常、当前观察
```

### 3.2 第二步：先查 UI 可见状态

按用户要求的页面顺序回读：

1. 设备是否启用、在线/过期/尚无数据；
2. 点位值、单位、数据类型、更新时间和质量；
3. 接入日志的主题、消息状态、错误摘要、规则和接收时间；
4. 计算定义的发布/运行状态、当前/历史窗口、质量、版本和运行记录；
5. 北向消费者的启用、授权、调用或投递状态；
6. UI 是否提供 Worker、队列、重试、确认和告警入口。

UI 看到的“有新数据”只说明页面读取到了某种新鲜度判断，不自动证明历史入库、计算完成或北向消费成功。

### 3.3 第三步：只读平台链路倒查

仅在 UI 事实明确后，按以下顺序核对平台侧：

```text
Topic 命中
  -> 消息接收状态
  -> 物模型/类型/单位校验
  -> 标准化值
  -> 原始/历史入库
  -> 事件或计算运行
  -> 结果质量/版本
  -> 北向查询或投递
```

每一跳只确认“是否到达、状态是什么、时间是否连续、错误是否可解释”。不得凭数据库中存在一行记录就推断 UI 已验收，也不得凭 API `200` 推断真实业务结果正确。

### 3.4 第四步：环境和启动层核对

由环境线程按[环境隔离规范](环境隔离规范.md)执行只读门禁：

- Git SHA、worktree、Compose SHA、镜像 digest、迁移账本是否一致；
- 容器、网络、Volume、挂载和端口是否属于同一环境；
- 数据库、EMQX、API、Ingester、Web 的分层健康/就绪状态；
- 重启次数、OOM、磁盘、临时文件和日志写入是否异常；
- 当前凭据是否来自受控存储（只确认存在和归属，不读取值）。

`healthy` 只代表该服务通过自己的健康检查，不能代替 MQTT 认证、订阅、入库、计算或 UI 业务验收。

### 3.5 第五步：采集层和外部条件核对

只有平台侧入口和环境边界已确认后，才把问题交给 Node-RED 专家或外部设备负责人：

- Node-RED：读取、解码、字段类型、时间戳、messageId、Topic 和重连；
- PLC/设备：开机、可达、FC01/FC03 只读响应和设备时钟；
- 网络/凭据：链路连通、认证授权和证书有效期；
- 北向消费端：合法隔离凭据、订阅/REST 路径和消费确认。

采集层问题必须保留平台收到前后的边界证据，不能只贴 Flow 截图就判平台失败。

## 4. 按现象选择入口

| 现象 | 第一观察点 | 下一跳 | 常见归因 |
| --- | --- | --- | --- |
| 设备“尚无数据” | 设备页最后数据和启用状态 | 接入日志是否有消息 | `NODERED`、`EXTERNAL` 或 `PLATFORM` |
| 有历史但长时间不更新 | 数据页更新时间/质量 | Topic 命中、认证、Ingester 消费 | `NODERED`、`EXTERNAL`、`PLATFORM` |
| 接收失败 | 接入日志错误字段和规则 | 物模型类型、单位、标识符 | 多为 `PLATFORM` 或 `NODERED` |
| 有接收但无历史 | 接收状态与历史时间对照 | 入库错误、事务和迁移状态 | `PLATFORM` 或 `ENVIRONMENT` |
| 计算“运行中”但无结果 | 计算页当前/历史/运行记录 | Worker、输入样本、质量原因、版本 | `PLATFORM`、`OPERATION` 或 `EXTERNAL` |
| 结果质量为无结果 | 质量和原因字段 | 输入新鲜度、窗口边界、规则版本 | 先记事实，不猜根因 |
| 北向无数据 | 消费者状态和最近调用 | 授权、Topic/REST、ACK/重试/去重 | `PLATFORM` 或 `EXTERNAL` |
| 重启后恢复异常 | 版本/挂载/凭据/迁移回读 | 运行时和采集连续性 | `ENVIRONMENT`、`NODERED` 或 `PLATFORM` |
| D/C 盘快速增长或 vmmem 飙高 | 磁盘、Docker、WSL、日志和进程 | 归属、owner、写入路径和阈值 | `ENVIRONMENT` 或 `EXTERNAL` |

## 5. 停止线和受控绕过

必须立即停止当前分支并回报：

- 需要写 PLC、发布测试 MQTT、读取或输出密钥；
- 需要跨环境、跨数据库或跨 Volume 操作；
- 迁移、恢复、seed、配置发布或重启会影响其他设备；
- 路径、owner、版本或回滚点不明；
- 连续两次失败且没有新增证据；
- 证据无法区分平台、采集层、操作和外部依赖。

可受控绕过但不能改写结论：

- 用后台只读回读补充 UI 未暴露的状态；
- 用隔离输入验证平台接收、计算或北向契约；
- 暂时跳过不受影响的设备/窗口，继续其他测试；
- 记录“绕过完成”，同时保留原 UI 或真实链路缺口。

绕过后必须写明：绕过动作、未验证的原始能力、是否影响结论、回滚/清理方式。

## 6. 证据和回执格式

每次排查至少生成一条脱敏回执，统一写入项目 `06_证据与验收`，包含：

```text
输入：任务来源、业务对象、设备编码、发生现象
动作：页面入口、只读检查、受控动作和停止线判断
结果：逐跳状态、实际值/时间/质量/错误码
证据：文件路径、编号、SHA-256、截图或回读位置
阻塞类型：PLATFORM / NODERED / OPERATION / ENVIRONMENT / EXTERNAL / JOINT
剩余风险：尚未确认的边界、未覆盖的窗口或外部条件
下一步：修复、补证、复测、转交或等待前置条件
```

证据不得包含密码、Token、证书、授权头或私密连接串。只记录凭据“存在/缺失/归属/哈希”，不记录值。

## 7. 归因、Issue 和复测

只有同时满足以下条件，才可把问题整理为平台 Issue：

1. UI、合法输入或受控只读链路已复现；
2. Node-RED、PLC、操作和外部依赖已排除或明确不在范围；
3. 复现条件、实际结果、业务影响和外部可观察验收标准完整；
4. Issue 只表达一个可独立关闭的结果。

Node-RED 问题进入采集层专项；操作和外部问题记录阻塞条件；联合问题先拆分边界。不要因为“暂时看不到入口”就断言后台不存在能力，应标记为 `UI/TOOL` 或 `BLOCKED` 并补证。

修复后必须使用独立验证集复测：更换时间、数据片段或自然生产事件，确认原问题消失且没有引入跨设备、历史、质量或资源回归。测试通过、服务 healthy 或后台绕过成功，都不能单独作为 Issue 关闭依据。

## 8. 最小交接摘要

每次排查结束时，用一段话交接：

```text
这是【业务对象/设备】的【现象】；已在【页面/链路】看到【事实】。
当前结论是【PASS/PARTIAL/FAIL/BLOCKED】，责任边界为【分类/层级】；
证据为【编号与 SHA】。尚未确认【边界】，下一步是【动作/前置条件】。
```

新线程拿不到任务卡正文、版本总账或最近回执时，状态只能是 `BLOCKED`，不得靠旧聊天或标题猜测继续执行。
