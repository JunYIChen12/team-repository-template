# IoT 平台测试体系：核心规则

## 体系身份

- 体系编号：`TEST-SYSTEM-IOT-001`
- 当前版本：`V1.3`
- 生效日期：`2026-08-31`
- 当前基线：每次测试必须填写实际 Git 完整 SHA、环境编码和证据索引
- 本文件定义测试证据和归因规则，不定义项目的启动、发布或实施顺序；项目执行顺序以[目标驱动的开发、运行与验收规范](../DEVELOPMENT_READINESS.md)为准
- 候选运行环境的版本、镜像、Secret、迁移和回滚以[候选环境交付契约](候选环境交付契约.md)为准
- 文件路径和文件名保持不变，避免已有 Project、证据和线程引用失效；以文档内版本号为准
- `IoT平台测试体系_软件工程校准_V1.0.md` 保留为历史详细版
- 详细用例继续使用独立测试矩阵，不在本总纲重复展开
- V1.3 补充开发测试阶段之间的边界、重测判定和 Issue 到验收证据的追踪要求

## 1. 核心目标

先验证真实业务结果，再判断平台能力；不先按已有功能设计“必然通过”的测试。

每个测试必须回答：输入是什么、做了什么、外部看到什么、证据在哪里、失败归谁。

## 2. 五层证据模型

1. **业务目标层**：说明要证明的现场事实、对象、范围和成功条件。
2. **场景测试集层**：用真实输入执行正常、异常、恢复和边界场景。
3. **独立验证集层**：换时间、数据或自然生产事件，重复验证同一目标。
4. **最终验收集层**：按真实交付方式完成 UI、查询、计算、北向和追溯验收。
5. **能力归因层**：前三层完成后，才判断是平台、Node-RED、操作、外部依赖或联合问题。

测试目标需要更强证据时，按以下方向深化；不适用的层必须标明后置或不适用，不能成为当前目标的默认阻塞：

```text
业务目标 → 场景测试集 → 独立验证集 → 最终验收集 → 能力归因 → 记录与收束
```

## 3. 测试任务格式

测试任务必须让没有历史聊天上下文的新测试人员独立执行。技术编号不能单独出现，必须同时提供业务名称、对象说明和稳定键。

### 3.1 任务身份与业务上下文

```text
测试编号：唯一编号，例如 20260824-49b54585-ING05
测试名称：用业务语言描述要验证的结果
业务目标：要证明的现场事实，以及为什么重要
业务对象：设备/产线/工序的中文名称
设备编码：稳定键，例如 PLC-102
对象词典：设备编码、设备名称、网关、Topic、物模型、点位的对应关系
业务输入：设备产生的真实数据或明确的隔离输入
技术输入：点位标识符、单位、数据类型、来源 Topic；不得只写内部 ID
测试范围：本任务验证什么
明确不在范围：Node-RED、PLC、操作、外部消费方或其他责任边界
```

### 3.2 前置条件与安全边界

```text
版本基线：Git 完整 SHA、worktree、Compose SHA、镜像 digest
运行环境：环境编码、端口、服务健康状态
权限条件：所需 UI 角色或受控测试账号
设备条件：设备是否开机、在线、允许只读采集
配置条件：设备、网关、物模型、Topic、计算定义是否已启用
数据条件：数据从哪里来、预计多久产生一次、如何判断数据有效
允许动作：页面观察、只读查询、受控重试等
禁止动作：PLC 写入、测试 MQTT 发布、输出密钥、越权写库
```

### 3.3 可执行步骤与观察点

每一步必须写清“在哪里操作、做什么、观察什么、保存什么”。

```text
步骤编号
操作入口：页面名称、Tab、设备或记录筛选条件
动作：具体点击、输入或只读观察
观察字段：状态、来源、时间、值、质量、错误码、版本等
预期：该步骤应看到的外部结果
证据：截图、页面回读或结构化回执编号
```

### 3.4 结果与归因

```text
实际结果：按步骤逐项填写，不能只写“正常/异常”
结果解释：把技术现象翻译成业务含义
结论：PASS / PARTIAL / FAIL / BLOCKED / NOT_APPLICABLE
能力归因：L1-L8
责任分类：PLATFORM / NODERED / OPERATION / EXTERNAL / JOINT
失败原因：已证实原因、当前线索、尚未确认项必须分开
复现条件：时间、设备、输入、版本和操作条件
绕过方式：如暂时使用后台，仅记录为绕过，不得写成平台已通过
```

### 3.5 交接摘要与可读性门禁

任务完成前，必须附上不超过一段的交接摘要：

```text
这是什么：业务对象和测试目的
测了什么：输入、主要操作和观察范围
结果怎样：通过/部分通过/失败，以及业务影响
谁负责：平台、Node-RED、操作、外部或联合
证据在哪：GitHub 摘要、本地证据编号和 SHA-256
接下来做什么：修复、补证、复测或等待前置条件
```

缺少业务对象、稳定键、输入、步骤、外部判定、证据或责任边界的内容，只能算测试主题，不能算可执行或已完成的测试任务。

任务来源必须可读取：GitHub Project 卡片正文是任务的唯一执行来源。派工时必须向执行线程提供卡片链接或完整正文；线程无法读取任务正文时，任务状态只能是 BLOCKED，禁止根据标题、旧聊天或猜测补齐缺失内容。

## 4. 八层能力归因

| 标签 | 归因范围 |
|---|---|
| L1 资源与配置管理 | 设备、网关、点位、地址、类型、单位、版本、发布 |
| L2 设备接入与采集任务管理 | 协议、采集周期、队列、超时、重试、断线识别 |
| L3 可靠采集与数据质量 | 时间、重复、乱序、缺失、延迟、跳变、补传、质量 |
| L4 数据存储与查询 | 原始值、标准值、历史、分页、时间范围、归档、恢复 |
| L5 数据处理、事件与计算 | 标准化、事件、窗口、累计差值、计算、版本、失败记录 |
| L6 业务上下文关联 | 工单、产品、批次、班次和设备业务引用 |
| L7 北向数据服务 | MQTT、REST、实时/历史、确认、重试、去重、限流、契约 |
| L8 平台治理、安全与运维 | 健康、监控、审计、权限、密钥、备份、恢复、回滚 |

问题分类只允许使用：

```text
PLATFORM / NODERED / OPERATION / EXTERNAL / JOINT
```

没有覆盖目标所需证据层时，不得直接写“平台缺陷”；必须保留缺失层和责任边界。

## 5. 责任边界

- **平台**：设备配置、数据接收、标准化、存储、查询、计算、北向和治理。
- **Node-RED**：PLC 读取、解码、边沿、序号和上报格式；作为采集层黑盒输入。
- **操作**：账号权限、配置步骤和测试动作。
- **外部依赖**：PLC、网络、设备开机状态和北向消费方。

Node-RED 内部实现问题不归入平台 Issue；操作问题和外部阻塞保留记录，但不冒充平台缺陷。

## 6. GitHub 与本地证据同步

测试结果必须分两层保存：

1. **GitHub Project**：每次任务执行后同步摘要，至少更新测试结论、能力归因、执行日期、基线短 SHA 和证据索引。
2. **本地证据目录**：保存完整回执、截图、日志摘要和 SHA-256；位置为 `D:\003_workspace\06_证据与验收`。

GitHub Project 卡片正文是测试任务的唯一来源。执行线程必须能读取该正文；无法读取时只能记录为 `BLOCKED`，不得用标题、旧聊天或后台猜测替代任务定义。

GitHub 只保存脱敏摘要和可定位索引，不写密码、Token、证书、授权头或私密连接串。

记录规则：

- `PLATFORM` 且证据充分：整理为 GitHub Issue。
- `NODERED`：记录到采集层专项，不进入平台 Issue。
- `OPERATION`、`EXTERNAL`：记录阻塞和复现条件，不提交平台 Issue。
- `BLOCKED`：更新 Project 状态和缺失前置条件，不能标记为失败或通过。
- 测试通过不等于 Issue 可关闭；关闭必须有修复后独立验证证据。
- GitHub 摘要必须使用业务名称，技术编码只能作为稳定键附在后面；不得只写“PLC-102”“ING-05”而不解释对象和目的。

### 6.1 不要因为“想确认一下”就重复测试

一次测试是否需要重跑，先比较测试身份：`Issue、契约版本、完整 SHA、测试命令、输入/fixture、环境和依赖`。所有条件都相同，就沿用原证据；只重新执行而没有新变化，不会产生新的结论。

| 变化 | IoT 中的正确动作 | 不能写成 |
| --- | --- | --- |
| 条件完全相同 | 不重跑，引用原回执 | “又测了一次，所以更可靠” |
| 平台代码或配置变化 | 先做改动直接影响的测试，再做受影响链路回归 | 只跑一个页面就宣布全链路通过 |
| 测试脚本、断言或 fixture 变化 | 先验证测试有效性，再做独立验证 | 用修改后的测试证明旧代码已修复 |
| PostgreSQL、Broker、镜像、依赖或权限环境修复 | 只重跑原来被挡住的测试层 | 把环境阻塞改写成平台失败或平台通过 |
| API、表结构、Topic、QoS、重试或设备契约变化 | 重新评审契约并生成新测试计划 | 继续沿用旧契约的通过证据 |
| 测试候选 SHA 变化 | 旧结果保留为历史，新 SHA 必须重新验证 | 混用两个 SHA 的日志和截图 |

连续两次失败但没有新证据时，应停止重复执行，先判断责任属于 `PLATFORM / NODERED / OPERATION / EXTERNAL / JOINT`。环境没有准备好时记 `BLOCKED`，业务结果错误时才记 `FAIL`。

### 6.2 四种测试各自能证明什么

通过某一层，只能证明这一层的事实，不能越级替代后面的验收：

| 测试层 | 能证明什么 | 不能单独证明什么 |
| --- | --- | --- |
| 自动化单元/契约测试 | 函数、服务规则和接口格式在固定输入下正确 | 真实 Broker、设备、权限和现场数据一定正常 |
| 任务级数据库/MQTT 集成测试 | 隔离环境中的存储、消息、迁移、去重、重试和服务连接正常 | 真实设备已经产生了正确业务结果 |
| 浏览器/API 验证 | 用户权限下页面、接口、实时/历史查询的外部结果正确 | 设备端采集和真实现场链路一定正确 |
| 独立数据/现场验收 | 换时间、换数据或按真实交付方式验证业务闭环 | 其他未覆盖能力自动通过 |

IoT 任务回执必须注明本次通过的是哪一层，以及还没有通过或没有验证的层。`PASS` 只对本层和本次绑定的基线负责。

### 6.3 Issue 追踪表

每个开放 Issue 都应有一行追踪记录；如果一个 Issue 拆成多个契约或测试，就继续增加行，不要覆盖历史：

```markdown
| Issue | 目标/非目标 | 契约版本 | 实现 SHA | 测试编号/命令 | 环境与输入 | 结论 | 责任分类 | 证据 | 验收人/下一步 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| #数字 | ... | ... | ... | ... | ... | PASS/PARTIAL/FAIL/BLOCKED | ... | ... | ... |
```

Issue 只有在契约已确认、实现已锁定、聚焦测试和受影响回归完成、必要的独立验证完成，并且证据和验收人都可追溯时，才允许关闭。测试通过、容器健康或页面能打开，都不能单独关闭 Issue。

## 7. 安全与资源门禁

- 测试前锁定 Git SHA、worktree、Compose SHA、镜像 digest、迁移账本、环境和设备编码。
- accepted、旧 candidate、当前 main 和运行环境不得混用。
- PLC 只允许 Modbus FC01/FC03 只读；禁止写 PLC、发布测试 MQTT 和猜测凭据。
- 密钥只在受控存储中使用，不进入普通配置、日志、证据或 GitHub。
- 新证据写入 `06_证据与验收`；临时资源写入 `08_临时缓存`，结束后确认无占用再清理。
- 未知资源保留，不因文件年龄或名称猜删。

## 8. 完成判定

一个测试任务只有同时满足以下条件才算完成：

- 陌生测试人员无需历史聊天即可理解业务对象、输入和目的；
- 执行线程已读取 GitHub Project 卡片正文并确认任务来源；
- 真实输入和实际操作已记录；
- 外部结果与预期标准完成对照；
- 结论属于五种状态之一；
- 能力归因和责任边界明确；
- 完整证据已落盘并有 SHA-256；
- GitHub Project 已同步摘要；
- 后续 Issue、责任方或复测条件已登记。

本规则只定义测试如何进行和如何记录，不代表平台已经具备任何能力。
