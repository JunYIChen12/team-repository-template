# IoT 平台开发、测试、交接与验收核心规则

## 体系身份

- 体系编号：`TEST-SYSTEM-IOT-001`
- 当前版本：`V2.0`
- 生效日期：`2026-09-01`
- 适用范围：IoT 平台、设备接入、采集、物模型、数据存储、计算、北向服务、运维和真实业务验收。
- 本文件定义一项任务从“发现问题”到“可以关闭 Issue”的共同做法。
- 本文件不替代团队仓库协作总规范、开发前置门禁、环境隔离规范和故障排查规范；它把这些规则在 IoT 任务中的执行顺序串起来。
- 文件路径和文件名保持不变，避免已有 Project、证据和线程引用失效；以文档内版本号为准。
- `IoT平台测试体系_软件工程校准_V1.0.md` 和 V1.x 历史版本保留为历史依据，不再作为新任务的执行入口。

## 0. 一页纸总规则

### 0.1 固定主线

每项非简单文字任务都按下面的顺序推进：

```text
真实问题
  → 唯一基线
  → 验收目标
  → 契约确认
  → 职责拆分
  → 开发与聚焦测试
  → PR 审查与交接
  → 隔离集成测试
  → 独立验证或真实验收
  → 关闭 Issue / 合并 / 发布
```

不能跳过前面的步骤，再用后面的结果补写前置条件。发现前置条件缺失时，状态写为 `NOT_READY` 或 `BLOCKED`。

### 0.2 五个事实必须分开

| 事实 | 它能说明什么 | 它不能说明什么 |
| --- | --- | --- |
| 代码完成 | 代码已修改并提交 | 功能已经测试通过 |
| 自动测试通过 | 固定输入下的规则或接口符合预期 | 真实设备和现场链路正常 |
| 隔离集成通过 | 任务级数据库、Broker、服务和权限可以连通并工作 | 真实业务闭环已经发生 |
| 真实验收通过 | 指定场景下用户看到的结果符合要求 | 其他没有覆盖的场景自动通过 |
| Issue 关闭 | 该问题已经有完整、可追溯的解决证据 | 所有相关问题都已经解决 |

### 0.3 三条停止线

遇到以下情况必须停下来记录，不得继续猜测或反复重跑：

1. 基线、契约、输入或验收标准不清楚。
2. 现象可能属于多个责任方，但还没有完成分层排查。
3. 连续两次失败，且没有新的代码、数据、环境或契约证据。

停止不是任务失败，而是保护团队不要在错误条件下继续消耗时间。

## 1. 术语、角色和状态

### 1.1 规范用词

- **必须**：没有满足时不能进入下一道门禁。
- **应**：默认要做；确实不能做时，必须记录原因、风险、替代措施、批准人和失效时间。
- **可以**：可按任务需要选择。

### 1.2 角色边界

一人可以承担多个角色，但每个角色的责任都要明确写在 Issue、Project 卡片或交接报告中。

| 角色 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 需求负责人 | 说明真实问题、范围、非目标和最终业务结果 | 不替开发预先指定实现细节 |
| 契约负责人 | 确认输入、输出、状态、错误、历史和兼容规则 | 不用代码默认行为代替契约确认 |
| 开发负责人 | 修改代码、补测试、说明影响和回滚 | 不把未验证的代码写成已验收 |
| 测试负责人 | 按测试层级执行并保存实际结果 | 不用页面、日志或健康检查越级证明其他层 |
| 集成负责人 | 验证数据库、Broker、服务、权限和外部依赖的连接关系 | 不把环境健康直接写成业务通过 |
| 验收负责人 | 按真实用户场景确认结果 | 不只看提交、构建或单元测试就验收 |
| 交接负责人 | 固定基线、证据、风险、停止线和下一步 | 不让聊天记录成为唯一交接资料 |

### 1.3 状态必须分开记录

任务状态、测试结论和 GitHub Issue 状态是三套不同的东西，不能互相替代。

**任务状态：**

| 状态 | 含义 |
| --- | --- |
| `NOT_READY` | 需求、契约、基线、环境或验收条件尚未准备好 |
| `IN_PROGRESS` | 前置条件已满足，正在开发或验证 |
| `CODE_COMPLETE` | 代码已完成并提交，但还没有完成全部验证 |
| `DEVELOPMENT_COMPLETE` | 聚焦测试、质量检查、审查和 Issue 回执已完成 |
| `DELIVERABLE` | 隔离环境运行、配置、权限、迁移和回滚证据已齐备 |
| `ACCEPTED` | 指定验收人确认真实业务结果 |
| `BLOCKED` | 有明确记录的前置阻塞尚未解除 |

**单项测试结论：**

`PASS`、`PARTIAL`、`FAIL`、`BLOCKED`、`NOT_APPLICABLE`。

GitHub Issue 只有 `OPEN` 或 `CLOSED` 等平台状态。Issue 保持 `OPEN` 不等于开发没有进展，关闭 Issue 也不能代替发布审批。

## 2. 信息应该放在哪里

为了不让不同地方各写一套说法，一项任务只允许有下面的分工：

| 载体 | 只记录什么 | 谁负责更新 |
| --- | --- | --- |
| Issue | 真实用户场景、实际问题、范围、非目标和可观察验收结果 | 需求/问题负责人 |
| 契约文档 | 已确认的输入、输出、状态、错误、历史、重试、幂等和兼容规则 | 契约负责人 |
| GitHub Project | 当前阶段、负责人、依赖、下一步和脱敏证据索引 | 交接或项目负责人 |
| PR | 本次修改、实现方式、验证结果、风险和回滚方式 | 开发负责人 |
| 测试回执 | 实际执行了什么、看到了什么、证据在哪里、失败归因是什么 | 测试负责人 |
| 交接报告 | 某个时间点的完整快照，让新同事可以继续工作 | 交接负责人 |

聊天可以用于讨论，不能作为唯一的需求、契约、测试或交接证据。讨论得出的决定必须回写到对应载体。

## 3. 阶段一：先写真实问题，不先写技术方案

### 3.1 一个 Issue 的最小内容

每个 Issue 应只对应一个可以独立判断的结果，并包含：

- **真实用户场景**：谁在什么情况下遇到问题。
- **实际遇到的问题**：用户看到了什么错误、缺失或不一致。
- **影响**：这个问题让用户无法完成什么，或带来什么风险。
- **复现方式**：需要什么前置条件、输入和操作。
- **期望看到的结果**：用户、接口、消息、历史记录或运维人员应该看到什么。
- **范围和非目标**：这次处理什么，明确不处理什么。
- **现有证据**：日志、截图、接口回执、测试编号或现场记录的脱敏索引。
- **负责人和依赖**：谁负责推进，等待谁或什么环境。

### 3.2 问题优先原则

Issue 里不要一开始写死下面这些内容：

- 指定要新增哪个字段；
- 指定必须使用哪张数据库表；
- 指定一定要采用哪种类、函数或消息结构；
- 指定开发人员必须选择哪种修复方式。

这些属于设计和实现讨论，应放到契约、设计记录和 PR。Issue 只需要把问题、影响和结果说清楚，给评审留下比较方案的空间。

如果某个技术事实已经确认，例如协议标准强制要求 QoS 1，应把它写成“已确认约束”，并附来源；不能把未经讨论的想法伪装成约束。

### 3.3 可复制的 Issue 模板

```markdown
# [问题类型] 简短的用户问题

## 真实用户场景
- 谁：
- 在什么情况下：
- 正在完成什么业务动作：

## 实际遇到的问题
- 实际看到了什么：
- 影响了什么业务结果：
- 是否有数据丢失、重复、错误或无法追溯：

## 复现方式
1. 前置条件：
2. 输入或现场事件：
3. 操作步骤：
4. 实际结果：

## 希望验收时看到的结果
- 用户可观察结果：
- 接口、消息、历史或审计结果：
- 失败时应该如何被发现：

## 范围
- 本 Issue 要解决：
- 明确不在本 Issue 内：

## 证据与依赖
- 现有证据：
- 当前基线或环境：
- 依赖和阻塞：
- 负责人：

## 讨论记录
实现方案放在关联契约、设计记录或 PR 中；Issue 不预设唯一实现方案。
```

## 4. 阶段二：开发前锁定基线和验收目标

### 4.1 开发准备门禁

开始写代码前，负责人必须在 Issue 或关联记录中填写：

```text
任务状态：NOT_READY / IN_PROGRESS
项目和仓库：
目标结果：
范围：
非目标：
负责人和协作角色：
验收人：
依赖和阻塞：
```

以下内容有一项没有确认，任务保持 `NOT_READY`：

- 真实问题、业务目标、范围和非目标明确；
- 验收人、验收环境、验收操作和通过条件明确；
- 当前基线、目标分支和回滚点明确；
- 输入数据、测试 fixture 或真实事件来源明确；
- 需要的 API、数据库、MQTT、设备和权限契约已找到或登记为待确认；
- 任务级数据库、Broker、容器、日志、端口和凭据边界明确；
- 允许动作和禁止动作明确。

### 4.2 基线登记

每次开发、测试和交接都必须记录完整版本信息，不能只写“最新代码”：

```text
规范版本：
项目仓库：
目标分支：
基线完整 SHA：
工作树路径：
Compose/配置完整 SHA：
镜像 digest：
数据库迁移账本：
运行环境编码：
设备、网关和对象稳定键：
测试证据目录：
```

基线必须能回到一个确定的提交和运行条件。`main`、candidate、accepted 标签、旧截图和当前运行环境不能混用。

## 5. 阶段三：先确认契约，再写实现

### 5.1 契约最小字段

任何会影响模块边界、数据库、接口、消息或设备链路的任务，都必须先确认对应契约：

| 契约部分 | 必须回答的问题 |
| --- | --- |
| 输入 | 允许什么字段、类型、单位、范围和来源？缺失或非法输入怎么办？ |
| 输出 | 返回什么字段、类型、单位、状态和时间？哪些字段对外可见？ |
| 状态 | 未开始、处理中、成功、失败、重试和最终失败分别叫什么？ |
| 错误 | 用户能看到什么错误？日志和外部响应如何脱敏？ |
| 历史 | 新规则影响未来数据还是历史数据？旧记录是否保留？ |
| 重试 | 重试触发条件、次数、间隔、最终状态和人工处理方式是什么？ |
| 幂等 | 重复请求或重复消息如何识别？是否允许同一 `messageId` 重复处理？ |
| 权限 | 哪些角色和 Topic 可以读、写、发布或订阅？ |
| 兼容 | 旧客户端、旧数据和旧配置如何处理？ |
| 非目标 | 明确哪些看起来相关但本次不做？ |

### 5.2 契约生命周期

```text
PROPOSED → CONFIRMED → IMPLEMENTED → VERIFIED → ACCEPTED
```

- `PROPOSED`：提出讨论，不能作为开发和测试的唯一依据。
- `CONFIRMED`：需求方、契约负责人和受影响角色确认，可以进入实现。
- `IMPLEMENTED`：代码已经按该版本实现，但还没有证明正确。
- `VERIFIED`：按绑定基线和测试计划获得了验证证据。
- `ACCEPTED`：指定验收人确认真实业务结果。

契约发生实质变化时，必须创建新版本，保留旧版本和旧证据，重新评审受影响的代码、测试、配置和外部消费者。不得修改旧契约后继续沿用旧的通过截图。

### 5.3 冲突处理

发现两个文档、Issue、代码或测试对同一行为有不同说法时：

1. 记录冲突双方和受影响范围。
2. 暂停受冲突影响的开发和验收。
3. 由需求负责人、契约负责人和受影响责任方确认最终规则。
4. 更新契约版本、Issue、测试计划和交接记录。
5. 重新验证，旧证据只证明旧规则。

冲突没有解决时，任务只能是 `BLOCKED`，不能写成“按最新理解完成”。

## 6. 阶段四：拆分职责和合作线程

### 6.1 拆分原则

一个线程或同事只负责一个可以交付、可以验证的目标。任务拆分时必须说明：

```text
子任务目标：
负责范围：
不负责范围：
输入契约版本：
输出物：代码 / 测试 / 文档 / 证据 / 评审意见
前置依赖：
完成条件：
不能越过的停止线：
```

线程是协作工具，不是新的事实来源。线程中的结论必须回写到 Issue、契约、PR 或测试回执，下一位同事不能只依赖线程上下文接手。

### 6.2 常见职责边界

| 责任分类 | 典型范围 | 处理原则 |
| --- | --- | --- |
| `PLATFORM` | 平台接收、校验、标准化、存储、查询、计算、北向和治理 | 满足前置条件后仍能稳定复现，才形成平台 Issue |
| `NODERED` | PLC 读取、解码、边沿、序号、Flow 和采集报文 | 记录到采集层专项，不把内部实现问题写成平台 Issue |
| `OPERATION` | 账号权限、保存发布、配置步骤和测试操作 | 记录操作条件和修正方式，不冒充产品缺陷 |
| `EXTERNAL` | PLC、设备、网络、Broker 或外部消费方 | 记录外部证据和阻塞，不推断平台已失败 |
| `JOINT` | 两个或多个责任方的接口或边界问题 | 指定每一方的证据和解除条件 |

没有完成输入、操作和外部依赖排查前，不得直接下结论为 `PLATFORM`。

### 6.3 八层能力归因

| 层级 | 归因范围 |
| --- | --- |
| L1 | 资源与配置：设备、网关、点位、地址、类型、单位、版本和发布 |
| L2 | 设备接入与采集任务：协议、周期、队列、超时、重试和断线识别 |
| L3 | 可靠采集与数据质量：时间、重复、乱序、缺失、延迟、跳变、补传和质量 |
| L4 | 数据存储与查询：原始值、标准值、历史、分页、时间范围、归档和恢复 |
| L5 | 数据处理、事件与计算：标准化、窗口、累计差值、计算、版本和失败记录 |
| L6 | 业务上下文关联：工单、产品、批次、班次和设备业务引用 |
| L7 | 北向数据服务：MQTT、REST、实时/历史、确认、重试、去重、限流和契约 |
| L8 | 平台治理、安全与运维：健康、监控、审计、权限、密钥、备份、恢复和回滚 |

责任分类和能力层级要分开填写，例如：`L7 + JOINT`，不能只写“平台问题”。

## 7. 阶段五：开发和提交

### 7.1 分支与工作树

- 从已登记的最新目标分支创建短期任务分支。
- 非简单改动使用独立 worktree，记录绝对路径。
- 一个分支只处理一个明确目标，不混入无关修复、格式化或个人环境文件。
- 分支名应能看出目的，例如 `codex/fix-calculation-contract`。
- 不直接向共享主分支推送，不强制推送，不改写共享历史。

### 7.2 开发中的最小循环

```text
修改一个小切片
  → 运行相关聚焦测试
  → 检查变更范围和敏感信息
  → 提交一个可回退 commit
  → 再开始下一个小切片
```

Commit 信息应说明目的，变更代码、测试和文档时可以拆成多个逻辑清楚的提交。不得把“构建成功”写成“业务验收成功”。

### 7.3 开发完成检查

进入 PR 前，至少确认：

- 修改文件都属于当前任务；
- 代码、测试、文档和配置使用同一个契约版本；
- 正常、异常和关键边界都有聚焦测试；
- 项目规定的格式、类型、静态和安全检查已执行，或记录了阻塞；
- 数据库、消息、权限和配置变化已经说明影响；
- 回滚方式明确；
- 当前状态准确写为 `CODE_COMPLETE` 或 `DEVELOPMENT_COMPLETE`，不提前写 `ACCEPTED`。

## 8. 阶段六：分层测试和真实验收

### 8.1 固定测试层级

```text
业务目标
  → 聚焦自动化测试
  → 任务级隔离集成测试
  → 独立数据或独立时间验证
  → 按真实交付方式验收
  → 能力归因与记录收束
```

| 测试层 | 能证明什么 | 不能单独证明什么 |
| --- | --- | --- |
| 业务目标 | 要证明的现场事实和用户影响 | 代码已经实现 |
| 聚焦自动化 | 函数、服务规则、迁移或接口在固定输入下正确 | 真实设备、Broker、权限和现场数据正常 |
| 隔离集成 | 任务级数据库、Broker、服务连接、消息、去重、重试和权限协作正常 | 真实生产业务结果已经产生 |
| 独立验证 | 换时间、换数据或换一次自然事件后，问题是否再次消失 | 未覆盖的其他能力自动通过 |
| 真实验收 | 指定用户场景按真实交付入口完成，外部结果符合契约 | 其他场景、设备和版本自动通过 |

每条回执必须写清“本次通过了哪一层”，以及哪些层还没有验证。`PASS` 只对本次绑定的 Issue、契约、基线、输入和环境负责。

### 8.2 测试任务模板

```markdown
## [测试编号] 测试名称
```

### 8.3 真实 UI、设备和北向边界

- 自动化测试不能代替真实 UI 验收。
- API、数据库或日志可以帮助定位，不能在要求 UI 时替代 UI。
- 模拟输入可以验证平台规则，不能证明 PLC 已经产生真实数据。
- Broker 中看到了消息，不能单独证明最终消费方完成业务处理。
- 容器 `healthy` 只证明对应健康检查，不等于数据入库、计算、消息投递或业务闭环成功。

## 9. 阶段七：避免无变化重复测试

### 9.1 测试身份

每次测试用下面这一组信息确定“到底测的是什么”：

```text
Issue + 契约版本 + 完整 commit + 测试命令 + 输入/fixture + 环境和依赖
```

条件全部相同时，原回执仍然是同一次测试。只为获得一个更新的时间戳而重跑，不能增加可信度。

### 9.2 重测判定表

| 变化 | 正确动作 | 不能写成 |
| --- | --- | --- |
| 条件完全相同 | 引用原回执，不重跑 | “又测了一次，所以更可靠” |
| 产品代码或配置改变 | 先测直接影响范围，再做受影响回归 | 只打开一个页面就宣布全链路通过 |
| 测试脚本、断言或 fixture 改变 | 先确认测试仍然有效，再做独立验证 | 用改过的测试证明旧代码已修复 |
| 数据库、Broker、依赖或权限环境修复 | 只重跑之前被挡住的测试层 | 把环境阻塞改写成产品失败或产品通过 |
| API、表、Topic、QoS、重试或设备契约改变 | 创建新契约版本并重新设计测试 | 沿用旧契约的通过证据 |
| 候选 commit 改变 | 保留旧结果，按新 SHA 重新验证 | 混用两个 SHA 的日志和截图 |

连续两次失败但没有新证据时，必须暂停重跑，先判断责任分类。环境没有准备好记 `BLOCKED`；业务结果错误才记 `FAIL`。

## 10. 阶段八：证据、PR 和交接

### 10.1 证据最小链条

每个 Issue 或测试任务都必须能沿着下面的链条回读：

```text
Issue
  → 契约版本
  → 设计/实现 commit
  → 测试编号与命令
  → 环境与输入
  → 实际结果
  → 脱敏证据
  → 验收人
```

链条中缺少一项，任务只能标记为 `PARTIAL` 或 `BLOCKED`；如果某项明确不适用，才使用 `NOT_APPLICABLE`，不能写成已完成。

证据分两层保存：

1. GitHub Issue/Project/PR 保存脱敏摘要、链接、结论、短 SHA 和证据索引。
2. 本地 `06_证据与验收` 保存完整回执、截图、日志摘要和 SHA-256；临时内容写入 `08_临时缓存`。

GitHub、Issue、PR、日志和截图中禁止出现密码、Token、证书、授权头、完整连接串、完整 JWT 或未经授权的客户数据。

### 10.2 PR 最小要求

PR 必须说明：

- 背景和真实问题；
- 关联 Issue；
- 基于哪个完整 SHA；
- 修改了什么，明确没有修改什么；
- 使用了哪个契约版本；
- 运行了哪些测试，哪些没有运行以及原因；
- 当前状态和未完成边界；
- 风险、回滚方式和后续负责人。

Issue 还没有满足关闭条件时，使用：

```text
Refs #编号
```

只有证据齐全、PR 已通过审查并且该结果确实已经完成时，才使用：

```text
Fixes #编号
```

一个 PR 可以关联多个 Issue，但必须说明它们是否共享同一个契约和验收结果。不同目标应拆成不同 PR。

### 10.3 固定交接报告

交接报告不能只写“代码已完成”，至少包含：

```markdown
# 交接报告

- 项目和仓库：
- 规范版本：
- 基线分支和完整 SHA：
- 工作分支和完整 SHA：
- PR：
- 当前任务状态：

## Issue 进度
| Issue | 用户问题 | 契约版本 | 实现 SHA | 已通过测试 | 未完成/阻塞 | 下一步 |
| --- | --- | --- | --- | --- | --- | --- |
| #编号 | ... | ... | ... | ... | ... | ... |

## 已确认契约
- 输入和输出：
- 状态和错误：
- 历史数据：
- 重试和幂等：
- 兼容和非目标：

## 证据
- 聚焦测试：
- 隔离集成：
- 独立验证：
- 真实验收：
- 本地证据目录和校验值：

## 停止线和风险
- 不能继续做什么：
- 为什么不能做：
- 解除条件：
- 回滚方式：

## 接手动作
1. 读取本报告、关联 Issue 和契约版本。

4. 只运行因代码、契约、数据或环境发生变化而需要重跑的测试。

```

接手人必须能够只根据报告、Issue、契约和仓库内容开始下一步工作；无法做到时，交接仍未完成。

## 11. 阶段九：验收、关闭和发布

### 11.1 Issue 关闭条件

一个产品 Issue 只有同时满足以下条件，才允许关闭：

- 真实用户场景和问题没有被偷换；
- 契约已经是 `CONFIRMED`，没有未解决冲突；
- 实现 commit 已锁定，且 PR 已完成审查；
- 聚焦自动化测试通过；
- 受影响的隔离集成测试完成；
- 必需的独立验证或真实验收完成；
- 实际结果、证据、基线、环境和验收人可追溯；
- 所有未覆盖项、风险和下一步已登记；
- 没有把后台旁路、容器健康或单次页面打开当成唯一依据。

如果某一层对本 Issue 确实不适用，必须写出“不适用原因”和批准人，不能默认为通过。

### 11.2 四个动作分开判断

```text
Issue 关闭：问题有完整解决证据
PR 合并：代码评审和检查通过
版本发布：发布清单、来源和回滚已确认
生产变更：有明确授权，并完成目标环境读回
```

其中一个动作完成，不代表其他三个动作自动完成。

### 11.3 发布和回滚

- 发布必须绑定明确的 commit 或 tag。
- 数据迁移、消息契约、权限和配置变化必须说明兼容性。
- 高风险变化必须在 PR 中写回滚路径、影响范围和负责人。
- 回滚通过新的 PR 或受控紧急流程完成，不改写共享主分支历史。
- 未验收的 candidate 不得标记为 `accepted`，也不得当作正式回滚基线。

## 12. 安全和资源门禁

- 测试前锁定 Git SHA、worktree、Compose SHA、镜像 digest、迁移账本、环境和设备编码。
- 任务使用独立的项目名、网络、容器、卷、数据库、日志、端口和临时凭据；资源归属必须可说清楚。
- 不读取、复制或输出稳定环境凭据；临时凭据遵循最小权限、可撤销和到期原则。
- PLC 只允许约定的 Modbus FC01/FC03 只读动作；禁止写 PLC、发布测试 MQTT 或猜测凭据。
- 不连接或修改生产数据库、生产 Broker、真实设备或共享测试库，除非完成单独授权和变更审批。
- 新证据写入 `06_证据与验收`；临时资源写入 `08_临时缓存`；结束时确认进程、容器、端口和挂载没有继续占用。
- 未知资源保留并报告，不因文件年龄、名称或大小猜测删除。

环境和故障的详细规则见：[环境隔离规范](环境隔离规范.md) 和 [故障排查规范](故障排查规范.md)。

## 13. Issue 追踪表

每个开放 Issue 至少保持一行；同一 Issue 拆成多个契约或测试时增加行，不覆盖历史：

```markdown
| Issue | 真实问题/范围 | 契约版本 | 基线 SHA | 实现 SHA | 测试层/命令 | 环境与输入 | 结论 | 责任/L层 | 证据 | 验收人/下一步 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| #数字 | ... | ... | ... | ... | ... | ... | ... | PASS/PARTIAL/FAIL/BLOCKED | ... | ... |
```

每次状态变化都应留下日期、操作者和变化原因。旧证据只能追加引用，不能被新结果覆盖。

## 14. 最小执行清单

### 开始前

- [ ] Issue 写清真实场景、实际问题、影响、复现和期望结果。
- [ ] 范围、非目标、负责人、验收人和依赖已登记。
- [ ] 基线完整 SHA、分支、worktree、环境和回滚点已锁定。
- [ ] 输入、契约、测试数据、权限和资源边界已确认。

### 开发中

- [ ] 职责和线程边界明确，没有两个线程做同一件事。
- [ ] 契约为 `CONFIRMED`，代码、测试和文档使用同一版本。
- [ ] 小步修改、小步测试、小步提交。
- [ ] 失败时保存实际结果，先归因再决定修复或重测。

### PR 和交接

- [ ] PR 只处理一个明确目标，已关联 Issue。
- [ ] 已区分运行了的测试、没有运行的测试和阻塞原因。
- [ ] 已记录基线、实现 SHA、证据位置、风险和回滚方式。
- [ ] 已生成交接报告，接手人可以不依赖聊天开始下一步。

### 关闭前

- [ ] 契约冲突已解决，且没有未登记的非目标。
- [ ] 聚焦测试、受影响回归、隔离集成和必要的独立/真实验收已完成。
- [ ] 证据、验收人、责任归因和复现条件可追溯。
- [ ] 只有真正完成的 Issue 使用 `Fixes #编号` 并关闭。
- [ ] 未验收、未合并、未发布和未部署的边界已经明确写出。
