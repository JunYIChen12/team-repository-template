# 可迁移环境隔离规范

## 目标

任何项目、电脑或版本都必须能够证明：当前运行的代码、配置、服务、数据和凭证属于同一个环境。

环境不一致时，禁止启动和测试。

## 第一性原理

1. 端口不能证明环境身份。
2. `localhost` 不能证明数据来源。
3. 浏览器能打开不能证明 API、数据库和 Broker 正确。
4. 容器重启不能保证凭证存在。
5. “测试通过”必须绑定代码、配置、数据和服务指纹。

因此，每个环境必须有唯一身份，并由启动门禁强制验证。

## 环境清单

每个环境固定一份 `environment.manifest.json`：

```json
{
  "project": "example",
  "environment": "stage1",
  "owner": "team",
  "purpose": "acceptance",
  "sourceSha": "<full-git-sha>",
  "composeSha256": "<compose-hash>",
  "dataRoot": "<runtime-root>/example/stage1",
  "network": "example-stage1-net",
  "resourcePrefix": "example-stage1"
}
```

必须固定：

- 完整 Git SHA；
- Compose/配置文件哈希；
- 数据根目录；
- 网络名和资源前缀；
- 所有者、用途和清理策略。

禁止用 `main`、`latest`、`localhost`、当前目录或端口作为环境身份。

## 资源规则

资源名称统一为：

```text
<project>-<environment>-<component>
```

容器、网络、卷和进程必须记录：

- `project`；
- `environment`；
- `owner`；
- `sourceSha`；
- `purpose`。

未标记或归属不明的资源不得自动使用或删除。

源码、运行数据和缓存分离：

```text
<workspace-root>/<project>/                 # 源码和 Worktree
<runtime-root>/<project>/<environment>/     # Compose、数据、日志、证据
<cache-root>/<project>/                     # 可重建缓存
```

## 唯一运行入口

禁止分别手工启动服务。每个项目只提供以下入口：

```text
env doctor
env up
env status
env test
env down
env clean
```

### `env doctor` 必须检查

- Worktree、Git HEAD 和 manifest 的 `sourceSha` 一致；
- Compose 和配置哈希一致；
- 容器、网络、卷属于当前环境；
- 端口没有被其他环境占用；
- 数据库、Broker、采集层挂载路径正确；
- 服务连接使用内部服务名，不使用隐式 `localhost`；
- 不连接共享、生产或旧环境数据库；
- 凭证来自当前环境的受控注入；
- 不存在未标记的旧资源连接到当前网络。

任一检查失败，`env up` 必须拒绝启动。

## Compose 规则

一次开发、测试或验收所需服务放在同一个 Compose 项目中，包括：

- 应用；
- 数据库；
- 消息代理；
- 采集/解析层；
- 测试辅助服务。

服务间只使用内部 DNS，例如：

```text
database:5432
message-broker:8080
collector:1880
```

禁止在容器内使用 `localhost` 或 `host.docker.internal` 连接项目数据库和 Broker，除非 manifest 明确声明并能验证目标身份。

## 凭证规则

- 凭证只通过受控 secret/env 注入；
- 外部服务加密密钥必须随环境持久化；
- 管理凭证和服务凭证必须属于当前环境；
- secret 不进入代码、Git、日志、截图、命令回显或证据；
- 凭证缺失时停止并请求人工接管，不猜测、不复用旧环境凭证。

## 版本更新

1. 保存当前 manifest 和运行快照；
2. 固定新版本完整 SHA 和镜像 digest；
3. 只替换允许更新的应用组件；
4. 保持数据、Broker 和采集层数据目录；
5. 重新运行 `env doctor`；
6. 启动、健康检查、再验收。

默认禁止自动执行：迁移、seed、fixture、清空数据、重置凭证、切换 enforcement、操作生产资源。

## 测试证据

每次证据必须包含：

- 环境 ID；
- 完整 Git SHA；
- Compose 哈希；
- 镜像 digest；
- 容器、网络、数据目录和端口；
- 凭证来源类别，不含 secret；
- 测试时间和结论。

结论必须区分：代码、用户操作、本地环境、凭证、外部设备或证据不足。

API、Mock、数据库或沙箱不能替代真实 UI、真实数据流和用户场景验收。

## 清理

允许清理：

- 当前任务的停止容器；
- 当前任务网络；
- 当前任务临时日志和缓存。

默认保留：

- 源码、Worktree、Git 历史；
- accepted 证据和快照；
- 数据库、Broker、采集层数据；
- 镜像和持久卷；
- 归属不明资源。

清理后必须回读容器、网络、端口、进程、数据目录和 Git 状态。

## 交接

交接包必须包含：

1. manifest；
2. Compose 和配置哈希；
3. Git SHA/tag；
4. 数据目录说明；
5. 凭证接管步骤，不含 secret；
6. 最近一次 `doctor/status` 收据；
7. 阻塞、恢复条件和清理边界。

新电脑恢复顺序：

```text
安装工具 → 克隆源码 → 校验 SHA → 恢复 manifest/secret/data
→ env doctor → env up → env status → 最小健康检查 → 用户验收
```

## 项目扩展

领域团队可以在本规范之上增加自己的约束，但必须明确标注为扩展，不得改变本规范的环境身份、启动门禁、资源归属、凭证隔离和证据要求。

扩展内容通常包括：

- 外部设备或硬件的安全操作边界；
- 特定协议的读写限制；
- UI、API、消息流或人工验收要求；
- 领域数据的备份、恢复和保留周期；
- 生产环境的部署、审批和回滚流程。

扩展应放在项目自己的运行手册或 ADR 中，不能把某个项目的端口、目录、服务名称或凭证规则写成本规范的通用前提。
